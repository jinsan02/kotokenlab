# 틀린 것 — 사건 기록과 다음 프로젝트로 가져갈 것

> **규칙은 여기에 없다.** 규칙은 [`RULES.md`](RULES.md), 기술적 함정의 본문은
> [`DESIGN_DELTA.md`](DESIGN_DELTA.md) §3 에 있다. 이 문서는 **실제로 틀린 일**
> 을 날짜순으로 모으고, 무엇이 그것을 잡아냈는지를 센다. 본문을 복사하지 않고
> 가리킨다.

## 왜 이 문서가 있나

이 저장소는 결함을 고칠 때마다 그 자리에 적어 왔다 — 도구 독스트링에,
`DESIGN_DELTA` 에, `HANDOFF` 표에, 커밋 메시지에. 고치는 데는 그게 맞다.
**그런데 그렇게 흩어 놓으면 "우리가 어떤 종류의 실수를 반복하는가" 를 볼 수 없다.**

여기서 세는 것은 개별 버그가 아니라 **패턴** 이다. 같은 종류가 네 번 났다면
네 번째를 고치는 것보다 그 종류를 막는 장치를 만드는 게 싸다. 실제로
`tools/compare_runs.py` 가 그렇게 나왔다.

## 2. 무엇이 실제로 잡아냈나

| 탐지 수단 | 건수 | 대표 사건 | 성격 |
|---|---:|---|---|
| 사람·외부의 감사 | 7 | 예산 지점/총량 · 예산 꼬리 회계 · 오염 미구현 | **결론을 바꾼 건이 전부 여기서** 나왔다 |
| 도구 출력을 넘기지 않은 것 | 4 | `compare_runs` "비교 불가" · R 369% | **"이상한데" 에서 멈춘 것.** 오늘 둘이 여기서 |
| 커밋 전 자기 검토 | 4 | 항상 참인 조건식 둘 · 과장된 dirty 문구 | 값싸다. 되돌릴 것이 없다 |
| 훅·검사기 (자동) | 3 | `run_id` 살균 · `record` 커밋 거부 | 확실하지만 **이미 돌린 뒤** 다 (40분 낭비) |
| 숫자가 이상해서 | 3 | 코드 BPB 가 7.6% 움직임 | 가장 불안하다. 못 느꼈으면 그대로 갔다 |
| 돌리기 전 점검 | 2 | `--eval-bytes` · `--pool-docs` | 가장 싸다. 이게 `compare_runs` 가 됐다 |

**읽는 법:** 자동 장치가 잡은 것은 전부 "형식" 이고, **결론을 바꾼 것은
하나도 자동으로 안 잡혔다.** 훅은 잘못된 커밋을 막지 잘못된 비교를 막지 못한다.
그래서 `compare_runs` 처럼 **판단을 코드로 옮기는** 도구를 계속 늘려 왔다.

## 3. 되풀이된 패턴 넷

### 패턴 A — 기본값이 조용히 다르다

`--eval-bytes` · `--max-bytes` · `--pool-docs` 로 **세 번**. 전부 "명시하지 않아서
기본값이 들어갔는데 기준값은 다른 숫자였다" 다. 한 번은 게이트를 거짓 실패시켰다.

> 비교할 run 은 **원장 `argv` 를 맞춘다.** config 는 불완전하다 — 나중에 생긴
> 필드는 옛 run 에 아예 없다.

### 패턴 B — 사람이 옮겨 적으면 갈린다

sigma, 판정표, BPB, 해시. **옮겨 적은 것은 전부 한 번씩 틀렸다.** 반올림 정밀도가
갈리거나, 파일 이름 순서로 읽어 값이 뒤바뀌거나, 앞자리만 보고 채우다 해시를
날조했다.

> 표는 코드가 원장에서 읽어 적는다. 보고도 그 표에서만 한다.

### 패턴 C — "모른다" 를 "같다" 로 읽는다

옛 config 에 없는 필드, 옛 정의의 `git_dirty`, 명목값 `n_shot=5`, 20MB 표본의
"0회". 전부 **없거나 불확실한 것을 확정으로 읽었다.**

> 세 갈래로 답한다: 같다 / 다르다 / **모른다**. 세 번째를 지우지 않는다.

### 패턴 D — 설계만 있고 구현이 없다

오염 제거 단계가 문서에는 있는데 코드에 없었다. R5 체크포인트 저장도 계획에만
있었다. **문서가 있으면 됐다고 느끼는 것** 이 원인이다.

> "적혀 있다" 와 "돌아간다" 는 다르다. 설계 문서의 각 단계에 그것을 실행하는
> 파일 경로를 적고, 없으면 없다고 적는다.

## 4. 다음 프로젝트에 가져갈 것

저장소와 무관하게 일반화되는 것만 적는다.

### 4-1. 판단을 도구로 옮겨라 — 사람이 매번 대조하는 것으로는 못 막는다

같은 종류를 네 번 하고서야 `compare_runs` 를 만들었다. 그리고 오늘, **그 도구가
못 보는 축(코드 계보)에서 내 손 대조가 4개를 놓쳤다.** 손으로 하는 점검은
정확도가 아니라 **범위** 에서 먼저 무너진다 — 나는 `src/training` 만 봤다.

> 점검을 두 번 손으로 했으면 세 번째에 도구를 만든다. 도구의 범위는 사람이
> 기억할 수 있는 것보다 넓게 잡는다.

### 4-2. 결과를 보기 전에 집계 도구를 써라

오늘 `seed_pairs.py` 를 run 이 도는 동안 만들었다. 그래서 `R` 이 영어에서
369% 가 나오는 것을 **데이터를 해석하기 전에** 발견했다. 결과를 본 뒤에 도구를
만들면, 이상한 값이 나왔을 때 그게 버그인지 발견인지 구분할 동기가 오염된다.

### 4-3. 되돌릴 수 없는 차이는 **생기기 전에** 적어라

회계 수정 때문에 새 run 의 예산 종점이 기존과 한 update 미만 달라질 것을
**돌리기 전에** PLAN 에 적었다. 끝난 뒤에 설명하면 같은 문장도 변명이 된다.
예측을 먼저 적는 것과 같은 이유다.

### 4-4. 자동 장치는 형식만 잡는다

훅·스키마 검사기가 잡은 4건은 전부 형식이었다. **결론을 바꾼 두 건은 사람의
감사에서 나왔다.** 자동화를 늘리되 "검사가 통과했으니 맞다" 로 읽지 않는다.

### 4-5. 세 갈래로 답하게 만들어라

`True` / `False` / **`None`**. `dirty_is_code_scoped()` 가 이 형태고,
`compare_runs` 의 "기록 없음" 도 그렇다. 이진으로 만들면 모르는 쪽이 반드시
편한 쪽으로 붙는다.

### 4-6. 과장은 경계에서 난다

"찍기 아래" (CI 가 0.25 를 포함) · "2σ 니까 95%" · 음수/음수로 나온 369%.
**전부 경계 근처의 값을 단정한 것이다.** 점추정만 적지 말고 구간·분모·정의
범위를 같이 적으면 대부분 저절로 막힌다.

### 4-7. 셸로 코드 파일을 쓰지 마라

heredoc 이 이스케이프를 실제 제어 문자로 바꿔 소스에 NUL 바이트를 박았다.
편집 도구를 쓰거나, 불가피하면 이스케이프 없이 쓴다.

## 5. 아직 안 막은 것

정직하게 남긴다.

- **near-dup 누수.** `split_audit.py` 는 정확 일치만 본다. 문구가 조금 다른
  문서는 못 잡고, 다시 검증하려면 본문이 필요하다
- **사전학습 오염.** Qwen 이 우리 dev/test 문서를 봤는지는 알 수 없다
- **동일 byte-context 비교.** BPB 는 고정 token-context 조건이다. 조건 간
  분모 차이는 재어 뒀지만(0.005%) 같은 원문 위치를 채점하는 평가는 없다
- **옛 run 의 반영 학습량.** `2da591e` 이전 run 은 복원할 수 없다. `NA` 로 둔다
- **`dirty=1` 인 옛 run 의 코드 상태.** 원장 행 때문인지 코드 때문인지 구분 불가
- **n=3 의 통계.** seed 3개로 낸 SD 와 t 구간은 전부 탐색적이다
