## 코어 — 이것만으로 완결된 이야기

```
Step 1  데이터 파이프라인      정규화 → dedup → 도메인 라벨 → 오염제거 → manifest → 문서단위 split
Step 2  Level 1 벤치마크       Qwen / HCX / A.X / Ours 를 같은 코퍼스에서 (도메인별)
Step 3  토크나이저 T0/T2a/T2b  T0 원본 · T2a vocab 축소 · T2b 크기유지 치환
Step 4  Surgery + E0/E1        resize(tied 유지), random vs mean 초기화, Pre-CPT 평가
Step 5  노이즈 플로어          동일 config 3 seed 로 σ_BPB 측정      ← 다른 모든 비교의 전제
Step 6  0.5B CPT               C0 통제군 필수, Equal Raw Data, 50M
Step 7  시스템 벤치마크         0.5B + 1.5B, 5k~40k자, raw_prompt / equal_tokens
Step 8  Level 3 + 최종 정리     capability, Final Test 1회, 표·그림, 리포트
```

### 명시적으로 하지 않는 것

`T1 Extend` · `T3 New BBPE` · `E2 Weighted` · `E3 Distillation` ·
`A0~A5 파라미터 범위 ablation` · `layer-wise CKA / gradient norm` ·
`Equal Token Budget` · `1.5B CPT`(추론 벤치마크만 함) · `3 seed 최종 반복`(노이즈 플로어에만 사용)

시간이 남으면 우선순위: **T1 → layer-wise 분석 → Equal Token Budget**.

## 사전 등록 질문 (pre-registration)

**실험 전에 고정한다.** 각 질문은 아래 셋 중 하나로 답한다.

```
개선     Δ > 2σ 로 좋아짐
구별 불가 |Δ| ≤ 2σ          ← 이것도 답이다. 유리한 쪽으로 반올림하지 않는다
악화     Δ > 2σ 로 나빠짐
```

σ 는 Step 5 에서 잰 노이즈 플로어다. 여섯 질문에 모두 답이 붙으면 프로젝트는 끝난다.

### 측정된 σ — 2026-08-30 확정

동일 config, seed 42/123/2026, 각 17.5MB 원문.
전체 표는 [`reports/tables/noise_floor.md`](../reports/tables/noise_floor.md).

| 조건 | 한국어 σ | 영어 σ | 코드 σ |
|---|---:|---:|---:|
| C0 (원본) | 0.000058 | 0.000058 | 0.000058 |
| **T2b (수술+E1)** | **0.001234** | 0.000058 | 0.000058 |

**σ 를 하나로 퉁치지 않는다.** 한국어에서 T2b 의 σ 가 C0 의 18.9배다 — 수술로
손상된 상태(BPB 2.38)에서 출발하면 seed 에 따라 회복 궤적이 갈리기 때문이다.
C0 의 σ 를 T2b 비교에 쓰면 차이를 18.9배 과대 검출한다.

> **2026-09-13 정정.** 위 배수는 전체 정밀도 σ 로 다시 계산한 값이다. 과거
> 표(21배)는 BPB 를 소수 4자리로 반올림해서 잰 σ 였다. 규칙 자체는 그대로다 —
> 조건별 σ 를 쓰고 두 조건 중 큰 쪽을 기준으로 한다.
> 표는 [`noise_floor.md`](../reports/tables/noise_floor.md) 에서 코드가 적는다.

두 조건을 비교할 때는 **큰 쪽 σ** 를 기준으로 판정한다. 조건이 늘어나면 그
조건의 σ 를 따로 재고, 재지 않았으면 "구별 불가" 로 남긴다.

이 σ 는 17.5MB 예산에서 나온 값이라 본 실험(50M 토큰)의 하한이다.

### 정렬 혼합비 — 사전 등록이 발동했고, 기준이 나빴다 (2026-08-31)

정렬 코퍼스의 언어 혼합비를 데이터로 고르기로 하고 판정 기준을 먼저 고정했다:
**영어·코드가 2 sigma(0.000115 BPB) 안에 머무는 비율 중 한국어가 가장 좋은 것.
어느 비율도 만족하지 못하면 멈추고 보고한다.**

세 비율(ko100 / ko80 / ko60) 모두 통과하지 못했다. 규칙대로 멈췄고 본 CPT 로
넘어가지 않았다. 전체 표는
[`reports/tables/alignment_probe.md`](../reports/tables/alignment_probe.md).

**기준 자체가 틀렸다.** ko60 의 영어 손해 +0.0299 BPB 는 기준의 260배로,
어떤 비율도 통과할 수 없었다. sigma 는 CPT 의 seed 노이즈를 잰 값이지 정렬이
낼 수 있는 손해의 척도가 아니다. 결과를 보고 기준을 완화하지는 않았고
(§107 evaluation freeze), 대신 다른 축(lr)을 갈라 정렬 단계 자체를 뺐다.

**다음 사전 등록에 옮길 교훈**: 임계값을 sigma 로 적기 전에 "무엇의 sigma 인가,
그 잡음원이 지금 재려는 효과와 같은 축인가" 를 먼저 답한다. 축이 다르면 sigma 는
임계값이 아니라 그냥 작은 숫자다.

### 답이 붙은 질문 — 2026-08-31

**Q4 — 동일 CPT 후에도 원본 토크나이저보다 language modeling 이 좋아지는가?**
**아니오.** 같은 원문 168.5MB 에서 T2b 는 한국어 BPB 1.5671, C0 는 1.1375 다.
343.7 sigma 로 악화이고 영어(+0.98%)·코드(+1.84%)도 나빠졌다. 압축 자체는
약속대로 됐다 — 같은 원문을 C0 는 49.9M, T2b 는 34.8M 토큰으로 처리했다
(비율 0.6977, 예측 0.696 과 일치). 문제는 압축이 아니라 회복이다.

**Q5 — vocab 을 줄이는 것(T2a)과 크기를 유지한 채 치환하는 것(T2b)은 다른
결과를 내는가?** **결정적으로 다르다.** T2a 는 C0 와 0.3% 안쪽인데 T2b 는
37.8% 나쁘다. 노이즈 플로어에서 나온 "수술을 받았는가가 아니라 수술로
손상됐는가" 가 CPT 후에도 그대로다.

전체 표: [`reports/tables/cpt_main.md`](../reports/tables/cpt_main.md).

### Phase 4 사전 등록 — 2026-08-31 확정

오늘의 진단(새 토큰 중앙값 발화 143회)이 가리키는 두 축을 따라간다.
**예측을 먼저 적는다. 틀리면 그게 더 중요한 발견이다.**

| 실험 | 질문 | 예측 |
|---|---|---|
| Equal Token Budget | 같은 **토큰수**(49.9M)를 주면 T2b 가 C0 를 따라잡는가 | **못 따라잡는다.** 최종 한국어 1.55 안팎, C0 와 0.41 차이 |
| N 스윕 (N=10,000) | 새 토큰을 1/3 로 줄여 노출을 3배로 하면 격차가 줄어드는가 | **줄지만 C0 를 넘지는 못한다** |

예측 근거 — T2b 는 20MB->168.5MB (8.4배) 동안 1.74->1.57 로 0.18 을 메웠다.
168.5->241.5MB 는 1.43배뿐이라 0.02 안팎이다.

**N=10,000 은 새 조건이므로 자기 sigma 를 따로 잰다** (17.5MB x 3 seed, 약 33분).
안 재면 판정은 규칙대로 "구별 불가" 로 남는다. T2b(N=30,000)의 0.001234 를
보수적 상한으로 써도 되지만 — 손상이 덜하니 실제 sigma 는 더 작을 것이고 큰
sigma 는 차이를 덜 검출하는 쪽으로만 틀린다 — 33분이면 실측할 수 있어 실측한다.

**N 스윕이 예측을 벗어나 C0 를 넘으면** "압축과 학습가능성 사이에 최적 N 이
있다" 는 새 주장이 성립하고, 프로젝트의 결론이 부정에서 조건부 긍정으로 바뀐다.
그 경우 N=20,000 을 추가로 재서 곡선을 그린다.

Phase 4 총 소요는 등토큰 1.7시간 + N 스윕 2시간 + sigma 0.6시간 = **약 4.3시간**.

### Q6 시스템 벤치마크 — 2026-09-01 사전 등록

**아직 안 돌렸다. 예측을 먼저 적는다.**

압축 -30.2% 가 품질에서는 값을 하지 못했다 (Q4 부정). 남은 물음은 **지연과
메모리에서는 값을 하는가** 다. 토크나이저를 바꾸는 실무적 이유가 여기 있고,
T2b 가 이길 수 있는 유일한 축이다.

**두 모드로 잰다.** 스키마의 `mode` 컬럼이 이걸 위해 있다.

| mode | 무엇을 고정하나 | 무엇을 답하나 |
|---|---|---|
| `raw_prompt` | 같은 **한국어 원문** | 실제 사용자가 겪는 차이. T2b 는 같은 글을 30% 적은 토큰으로 넣는다 |
| `equal_tokens` | 같은 **입력 토큰 수** | 개선이 시퀀스 길이에서 오는가, vocab 크기에서 오는가를 가른다 |

`equal_tokens` 의 T2b vs C0 는 **널 대조군** 이다. vocab 도 아키텍처도 같으므로
차이가 나오면 안 된다. 나오면 계측기가 고장난 것이다.

**대상**: CPT 를 마친 체크포인트 3종 (실제로 배포할 물건).
C0 · T2a(vocab 121,728) · T2b(vocab 151,936).

**길이**: 한국어 원문 5,000 / 10,000 / 20,000 / 40,000자.
40,000자는 약 27,300 토큰으로, 실측상 안전한 상한 근처다
([`reports/tables/resource_probe.md`](../reports/tables/resource_probe.md)).

#### 예측

| # | 예측 | 근거 |
|---|---|---|
| 1 | `raw_prompt` 에서 T2b 의 KV cache 가 **정확히 -30.2%** | 토큰 수에 선형이다. 이것이 안 맞으면 계측이 틀린 것 |
| 2 | `raw_prompt` 에서 T2b 의 prefill 이 **-33~42%** — 토큰 감소율보다 크다 | prefill 은 초선형이다. 실측 기울기가 1,024→4,096 구간 1.1 에서 16,384→32,768 구간 1.47 로 올라간다. 0.698^1.1=0.67, 0.698^1.5=0.58 |
| 3 | `equal_tokens` 에서 T2b ≈ C0 (**구별 불가**) | 널 대조군. vocab·아키텍처 동일 |
| 4 | `equal_tokens` 에서 T2a 의 peak_alloc 가 **약 54MB 낮다** | embedding 27.1M x bf16 2바이트. prefill 은 `logits_to_keep=1` 이라 lm_head 가 1행만 곱하므로 시간 차이는 거의 없어야 한다 |

**2번이 Q6 의 본체다.** "이론 감소율과 실측의 괴리" 라는 질문에 대한 답은
*괴리가 T2b 에게 유리한 쪽으로 난다* 여야 한다 — 토큰이 30% 줄면 시간은 30%
보다 더 준다. 이것이 확인되면 **압축의 값어치는 품질이 아니라 시스템에 있다** 는
결론이 서고, 부정 결과였던 프로젝트가 조건부 권고를 낼 수 있게 된다.

#### 측정 규약 ([RULES.md](RULES.md) 9번)

warm-up 후 `torch.cuda.synchronize()`. mean / median / std / P95 를 모두 남긴다.
attention 은 `EFFICIENT_ATTENTION + CUDNN_ATTENTION` 안에서만 (강제 안 하면
8,192 토큰에서 메모리 7.1배, 시간 10.3배).

**반복 횟수는 경로마다 다르게 잡고 원장에 남긴다.** prefill 은 warm-up 20 /
측정 100 회. 생성 경로(TTFT·decode)는 한 회가 수 초라 warm-up 5 / 측정 20 회로
줄인다 — 규칙이 요구하는 것은 고정된 100 이 아니라 `n_warmup`·`n_runs` 를
비우지 않는 것이다. 줄인 사실이 컬럼에 남는다.

프롬프트는 `data/interim/docs/dev.jsonl` 에서 만든다. **final_test 는 열지 않는다.**

#### 구현 계약 — `latency.py` 와 `memory.py` 는 아직 스텁이다

내일은 측정 전에 구현부터다. 두 모듈이 채워야 할 것:

```
latency.prefill(model, ids, n_warmup, n_runs) -> dict
    logits_to_keep=1 로 생성 경로와 같은 모양을 만든다.
    반환: mean/median/std/p95 (ms)

latency.generate(model, ids, gen_tokens, ...) -> dict
    반환: ttft_ms(mean/p95), decode_tok_s_mean, total_ms(mean/std)

memory.snapshot() -> dict
    peak_alloc_mb, peak_reserved_mb. 측정 전 reset_peak_memory_stats.

memory.kv_cache_mb(config, n_tokens) -> float
    n_layers x n_kv_heads x head_dim x 2(K,V) x 2바이트 x n_tokens.
    실측이 아니라 이론값이므로 컬럼 이름도 kv_cache_mb_est 다.
```

### Phase 6 — 사전 등록 (2026-09-02, Q1~Q6 이후)

코어는 닫혔다. 아래 셋은 **결론의 유효 범위** 를 정하는 후속이다.
전부 돌리기 전에 예측을 적는다.

#### A. 스케일 — 이 부정 결과가 0.5B 만의 것인가

우리 결론 전체가 **임베딩이 모델의 27.6% 인 곳** 에서 나왔다. 1.5B 는 15.1%,
7B 는 5.1% 다. Qwen2.5-1.5B 는 vocab 도 merges 도 0.5B 와 완전히 같으므로
**같은 토크나이저 산출물을 그대로 얹을 수 있다** — 학습 없이 수술 + Pre-CPT
BPB 만 재면 30분이다.

0.5B 의 손상 배율은 2.3803 / 1.1569 = **2.058배** 였다. 두 가설이 다른 값을 낸다.

| 가설 | 1.5B 예상 손상 배율 |
|---|---|
| H1 임베딩 비중에 비례 | 1 + 1.058 x (15.1/27.6) = **약 1.58배** |
| H2 스케일 무관 | **약 2.06배** |

**예측: H1 쪽, 1.5~1.7배.** 기전이 "얼어붙은 표현 공간에 새 행을 끼워 넣는
것" 이라면 그 행이 모델에서 차지하는 몫이 작을수록 손해도 작아야 한다.

H2 로 나오면 **결론의 적용 범위가 넓어진다** — 작은 모델의 아티팩트가 아니라
치환 자체의 성질이다. 어느 쪽이든 답이다.

#### B. 65% 는 벽인가 예산 부족인가

세 조건의 회복률 곡선이 1%p 안에서 겹친다. 손상 크기와도 노출과도 무관하고
예산만의 함수로 보인다. 그런데 **상한이 안 보인다** — 168.5MB 에서 65.4%,
241MB 에서 68.2% 로 예산 1.43배에 +2.8%p 다.

같은 100MB 지점에서 짧은 예산 run 이 65.0%, 긴 예산 run 이 66.9% 다.
같은 데이터량에서 1.9%p(19 sigma) 갈리는 것은 코사인 LR 이 덜 식었기
때문이다. 즉 **곡선이 천장에 닿은 게 아니라 LR 이 꺼지면서 멈춘 것이다.**

**예측: 500MB 예산에서 71~73%.** 로그선형 외삽이다. 이보다 낮으면 진짜
포화이고, 높으면 예산이 더 사줄 여지가 있다.

#### C. 기울기 계측 — 안 켠 계측기

`train_curve` 에 `grad_norm_emb` / `attn` / `ffn` 컬럼이 있는데 전부 NA 다.
학습 루프가 채우지 않았다. 기전에 대한 **직접 증거** 를 낼 수 있는 자리를
비워 뒀다.

**예측: 임베딩 기울기가 죽지 않는다.** BPB 가 멎은 뒤에도 attn/ffn 과
같은 자릿수로 남는다. 그것은 **BPB 정체 뒤에도 기울기 신호가 남는다** 는
관측이며, 그것만으로 병목의 원인을 특정하지는 못한다.
기울기가 실제로 죽는다면 그건 예측이 틀린 것이고 더 중요한 발견이다.

#### E. 배치 처리량

Q6 는 배치 1 단일 요청이다. "메모리를 30% 아끼므로 요청을 1.4배 받는다" 는
지금 표로 뒷받침되지 않는다.

**예측: 동시 처리 가능 수는 KV 절감만큼(약 1.43배) 늘지만, 처리량 이득은
그보다 작다.** 배치가 커지면 연산이 먼저 병목이 되기 때문이다.

### R1~R3 의 행 선택 규칙 — 2026-09-07 사전 등록

R1·R2·R3 은 토크나이저를 고정한 채 임베딩 행 K개를 망가뜨린다. **어느 K개인지가
안 정해져 있었다.** 안 정하고 시작하면 결과를 보고 고르게 된다.

```
count_ko 내림차순 상위 K개
  - protected (byte fallback 256 + special) 제외          RULES 12c
  - merges 에 부모가 없는 원자 토큰 제외                    부품 평균이 정의 안 됨
  - 손상 종류 셋이 **같은 행 집합** 을 쓴다                 R2 가 행 선택을 비교하지 않도록
```

빈도로 고르는 이유: T2b 가 치환한 30,000개는 코퍼스가 거의 안 쓰던 토큰이었고
(T2a 가 공짜였던 이유), 그 자리에 들어간 것은 자주 발화하는 한국어 토큰이었다.
1차의 손상은 "자주 쓰이는 행이 틀린 벡터를 들고 있다" 이므로, 안 쓰이는 행을
고르면 손상이 잡히지도 않는다.

이 규칙은 `damage_rows.py` 의 config `select_rule` 로 모든 run 에 박힌다.

#### K = 40 — 2026-09-07 보정 완료, 확정

학습 없이 Pre-CPT BPB 만으로 K=0~1,000 을 훑어 1차 T2b 의 손상 배율
**2.058배** (2.3803 / 1.1569) 를 재현하는 K 를 골랐다. 전체 표는
[`k_calibration.md`](../reports/tables/k_calibration.md), run `eval_kcal_mean_kcal{,2,3}`.

```
K=0     ko 1.1569   1.000배   <- 1차 Pre-CPT 표와 정확히 일치
K=40    ko 2.3633   2.043배   <- 채택. 목표 2.058 에 가장 가깝다
        (1차 T2b   2.3803   2.058배)
```

부수 피해도 맞는다 — K=40 에서 영어 +0.6%, 코드 +0.3% 로 T2b(+0.1% / +0.6%)와
같은 자릿수다.

**행 40개가 치환 30,000개와 같은 손상을 낸다.** 손상은 몇 행인가가 아니라
어느 행인가로 정해진다.

이 값으로 R1 을 돌린다. **결과를 보고 K 를 다시 고르지 않는다.**

#### R3 의 K = 10 / 40 / 160 / 640 — 확정

원래 등록했던 `1k / 10k / 30k / 100k` 는 무의미했다. K=1,000 이 이미 3.114배이고
`count_ko` 커버리지가 73.3%(1k) -> 83.0%(100k) 로 포화한다 — 네 점이 사실상
한 점이다. 1차에서 배치 목록을 2의 거듭제곱으로 잡아 1.4배 차이를 같은 칸에
묻었던 것과 같은 실수다.

보정된 K=40 을 가운데 두고 4배씩 벌린다. 손상 배율이 실제로 갈리는 구간이다:

```
K=10   1.502배      K=40   2.043배      K=160  약 2.5배      K=640  약 3.0배
```

**K=640 은 부수 피해가 다르다.** K>200 에서 영어가 무너지기 시작한다
(K=300 +3.9%, K=1,000 +29%). 그 점을 보고할 때는 영어·코드 BPB 를 함께 적고,
"1차와 같은 종류의 손상" 이라고 부르지 않는다.

### Q7 — tie 를 끊는다 (2026-09-03 사전 등록, P2 의 본안)

2차 설계는 [`SPEC_P2.md`](SPEC_P2.md) 에 있고, Q7 은 그 문서의 **R4** 다.
실행 설계는 [`SPEC_P2.md` §9](SPEC_P2.md) 에, 사전 등록은 여기에 둔다.
**돌리기 전에 고정한다. 결과를 보고 이 절을 고치지 않는다**
([RULES.md](RULES.md) 14번).

#### 가설

```
H    65% 회복 정체의 원인은 tie_word_embeddings=true 구조다.
     입력 임베딩과 출력 lm_head 가 같은 텐서라, 새 토큰의 입력 표현을 고치는
     방향과 출력 분포를 고치는 방향이 한 파라미터 위에서 충돌해 회복이 멈춘다.

H0   tie 를 풀어도 회복률이 tied 와 노이즈 범위 안에서 같다.
     그러면 병목은 tie 가 아니고, 다음 후보는 ALM(Cross-Tokenizer Distillation) 이다.
```

#### 예측

**회복률이 오른다. 72~78%.** 1차의 세 조건이 65.4 / 65.9 / 68.2% 로 겹쳤고,
예산 1.43배가 산 것이 +2.8%p 였다. tie 가 진짜 병목이라면 그보다 큰 폭이어야
가설이 살아 있다고 말할 수 있다.

**영어 BPB 는 나빠지지 않는다.** 노름 보정 때 영어가 함께 나빠진 것
([precpt_bpb.md](../reports/tables/precpt_bpb.md))은 새 토큰의 로짓이 softmax
분모를 통해 모든 문맥을 침범했다는 뜻이었다. tie 를 끊으면 그 경로가 사라진다.
영어가 **여전히** 나빠지면 그 해석이 틀린 것이고, 그게 더 중요한 발견이다.

#### 대조군 — 이게 없으면 실험이 성립하지 않는다

tie 를 끊으면 `lm_head` 가 새로 생겨 파라미터가 **494,032,768 → 630,167,424
(+136,134,656, +27.6%)** 늘어난다. untied-T2b 가 더 잘 회복해도 그것이
"tie 를 풀어서" 인지 "파라미터가 늘어서" 인지 가릴 수 없다.

**untied-C0 을 반드시 같이 돌리고, 회복률의 기준선을 tied-C0 이 아니라
untied-C0 의 BPB 로 잡는다.** 이 대조군을 뺀 설계는 채택하지 않는다.

#### 판정 수식

1차 정의([phase4.md](../reports/tables/phase4.md))의 분모만 바꾼다.

```
              B0(cond) − Bf(cond)
R_untied  =  ─────────────────────
             B0(cond) − Bf(untied-C0)
```

세 항이 **같은 예산 · 같은 seed 집합** 에서 와야 한다.

| 항 | 168.5MB 판정 | 17.5MB 게이트 |
|---|---|---|
| `B0` | 2.380297 (아래 상수 절 참조) | 2.380297 |
| `Bf(cond)` | S4 의 untied-T2b final | S2·3 의 untied-T2b final |
| `Bf(untied-C0)` | S4 의 untied-C0 final | S2·3 의 untied-C0 final |

**17.5MB 게이트의 분모에 168.5MB 의 바닥을 넣지 않는다.** 그 run 이 도달할
기회조차 없던 값과 재는 셈이 된다.

#### 판정 규칙 — 2σ 만으로는 부족하다

분모가 사실상 상수이므로 σ 는 그대로 전파된다.

```
sigma_R  ~=  sigma_BPB / (B0 − Bf(untied-C0))
```

17.5MB 에서 tied T2b 의 `sigma_BPB` 는 **0.001234** 였다(위 σ 절). 분모 1.2306 을
넣으면 **sigma_R ~= 0.10%p, 2sigma ~= 0.20%p** 다. 즉 **ΔR 이 0.3%p 만 나와도
형식상 2σ 를 통과한다.** 1차에서 65.4 / 65.9 / 68.2% 를 "같은 벽" 이라고 부른
판단과 정면으로 어긋난다.

그래서 **효과 크기 바닥을 함께 건다.**

```
H 지지        ΔR >= 5%p   AND   Δ > 2sigma
구별 불가     그 밖의 전부
H 반대        ΔR <= −5%p  AND   Δ > 2sigma
```

**5%p 의 근거**: 1차에서 조건 간 실제 격차가 0.5~2.8%p 였고 우리는 그것을
"움직이지 않았다" 로 읽었다. 5%p 는 그 해석과 모순되지 않는 최소값이다.
이 값은 **지금 정한다.** 결과를 본 뒤에 정하면 §107 evaluation freeze 위반이다.

#### 구성상 고정된 상수 — S1 은 발견이 아니라 게이트다

`lm_head` 를 embedding 사본으로 만드는 untie 는 **forward 를 바꾸지 않는다.**
2026-09-03 에 CPU 에서 저장·재적재까지 확인했다 — 같은 입력의 logits 가 tied
원본과 `torch.equal` 로 동일했고, safetensors 에 `lm_head.weight` 가 실려
`config.tie_word_embeddings=false` 로 남았다.

따라서 학습 전 BPB 는 **달라질 수 없다**:

```
B0(untied-T2b)  ==  2.380297        B0(untied-C0)  ==  1.156880
```

S1 에서 이 값이 안 나오면 그것은 발견이 아니라 **untie 가 깨진 것** 이고,
거기서 멈춘다. S1 의 목적은 초기 손상 비교가 아니라 정합성 게이트다.

#### 노이즈 플로어 — 어느 예산에서 재는가

untied 는 새 조건이므로 σ 를 모른다. **측정 전에는 어떤 차이도 유의하다고
말하지 않는다.** 다만 예산별로 출처가 다르다.

| 쓰이는 곳 | σ 출처 | 비용 |
|---|---|---|
| S2·3 의 중단 게이트 (17.5MB) | S2·3 자체가 seed 42/123/2026 이다 | 이미 포함 |
| S4 의 최종 판정 (168.5MB) | **S4 의 3 seed 에서 직접 나온다** | 이미 포함 |

[`SPEC_P2.md` §5](SPEC_P2.md) 의 "σ 는 실제 예산에서" 규약을 이렇게 지킨다 —
1차처럼 17.5MB 의 σ 를 168.5MB 판정에 빌려 쓰지 않는다.

#### 중단 기준

S2·3(17.5MB) 에서 untied 의 회복률이 같은 예산의 tied 회복률과 **위 판정
규칙으로 "구별 불가"** 면, H 는 지지되지 않는 것으로 보고 **S4 를 돌리지 않고
정리한다.** 1차에서 세 조건 곡선이 1%p 안에 겹쳤다는 사실이 이미 "조건을 바꿔도
곡선이 안 움직인다" 쪽의 증거다. 이번에도 그러면 그게 결과다.

같은 예산의 tied 기준값은 원장에 있다 (설계 시점에 아래 행에서 산출):

```
B0                2.380297
Bf(tied T2b)      1.860251   cpt_t2b_mean_noise_{seed42,seed123,seed2026} 평균
Bf(tied C0)       1.149698   cpt_c0_qwen_noise2_{seed42,seed123,seed2026} 평균
R_tied@17.5MB     0.520046 / 1.230599 = 42.26%
```

**반증이 나오면 그것도 성과다.** 긍정 결과를 찾으러 가지 않는다. 1차의 주요
발견 셋은 전부 반증이었고 그게 이 저장소의 가치다.

### R5 의 경쟁 등록 B — 상수 LR 로도 못 넘는다 (2026-09-13 사전 등록)

[`SPEC_P2.md`](SPEC_P2.md) 의 R5 는 2026-09-03 에 이미 등록돼 있다 —
**"넘는다. 71~75%"**. 그 등록은 **고치지 않는다** ([RULES.md](RULES.md) 14번).

2026-09-13 에 1차 곡선을 사후 분석한 결과가 **반대 방향을 가리킨다**
([`plateau_nulls.md`](../reports/tables/plateau_nulls.md)). 등록을 바꾸는 대신
경쟁하는 두 번째 예측을 같은 실험에 건다. **R5 가 둘 중 하나를 죽인다.**

#### 무엇이 달라졌나

등록 A 의 근거는 [`phase6.md`](../reports/tables/phase6.md) 의 방증 둘이었다.

- 80 -> 100MB 에서 기울기가 3.05 -> 3.39 로 오르는데 lr 은 6.0e-06 -> 4.3e-06 으로 떨어진다
- 같은 100MB 지점에서 짧은 예산 run 65.0% vs 긴 예산 run 66.9%

사후 분석은 그 방증을 정량으로 다시 쟀다.

```
-ln(1-R) 을 integral(lr dD) 로 미분한 값    921 -> 30              31배 감속
같은 구간의 lr 자체                         9.78e-06 -> 1.06e-06    9.2배
```

**LR 로 정규화하고도 31배 감속이 남는다.** LR 이 감속의 주원인이면 이 값이
상수여야 한다. 아니므로 상수 LR 이 벽을 뚫지 못할 것으로 본다.

#### 예측

```
등록 A (2026-09-03)   상수 LR 에서 R = 71~75%.   LR 이 회복을 끊고 있었다
등록 B (2026-09-13)   상수 LR 에서 R <= 68.5%.   감속은 LR 이 아니다
```

68.5% 의 근거: 1차에서 예산 43% 증가가 산 것이 +2.8%p(65.4 -> 68.2%)였다.
상수 LR 이 LR 감쇠분만 돌려준다면 그 정도 크기를 넘지 못한다.
두 예측 사이에 **2.5%p 의 빈 구간(68.5~71%)** 이 있고, 거기 떨어지면
**둘 다 틀린 것으로 보고한다.** 사후에 어느 한쪽으로 당기지 않는다.

#### 판정

판정 sigma 는 **R5 자체의 3 seed** 에서 나온다 — 1차 sigma 를 빌리지 않는다
([`SPEC_P2.md` 5절](SPEC_P2.md)).

| 결과 | 뜻 |
|---|---|
| R >= 71% | 등록 A 지지, B 기각. LR 이 회복을 끊고 있었다 |
| R <= 68.5% | 등록 B 지지, A 기각. **정체는 스케줄의 산물이 아니다** |
| 68.5 < R < 71 | 둘 다 기각. 그대로 보고한다 |

가운데 칸이 나오면 그것도 답이다. 두 예측 다 우리가 낸 것이고, 실험이 가른다.

#### 결과 (2026-09-16) — 등록 A 지지, 등록 B 기각

```
T2b 상수 LR 3 seed   Bf 1.473036 / 1.472577 / 1.473207
C0  상수 LR 1 seed   1.127397     <- 앵커 발동 조건(66.0~73.5%)이 켜져 돌렸다
R (상수 앵커)         72.42%   sigma_R 0.026%p
```

71% 이상이므로 **등록 A 지지.** 등록 B 는 틀렸다. N2 의 관측(LR 정규화 후에도
31배 감속)은 그대로 맞지만, 거기서 "상수 LR 도 못 넘는다" 로 건너뛴 추론이
틀렸다. 이 절은 결과를 보고 고치지 않았다 — 이 문단만 결과로 덧붙였다.
기록 `23237cc` · `64556e2`.

#### 사후 분석이라는 사실을 숨기지 않는다

[`plateau_nulls.md`](../reports/tables/plateau_nulls.md) 의 N1~N3 은 1차 사전

**문항** — 6과목 test 전부. 수는 받은 뒤 코드가 센다. 일부만 고르지 않는다.

**프롬프트 · shot**

```
5-shot. 예시는 같은 과목의 dev 5문항, 파일 순서 그대로
형식   {question}\nA. {A}\nB. {B}\nC. {C}\nD. {D}\n정답: {letter}
       예시 사이는 빈 줄 하나. 마지막 문항은 "정답:" 에서 끝난다
```

shot 수는 **C0 토크나이저로 잰 프롬프트가 2048 토큰(CPT seq_len) 안에 들 때까지
앞쪽 예시부터 뺀다.** 이렇게 정한 프롬프트 **문자열을 모든 모델에 그대로 준다** —
모델마다 shot 수가 달라지면 토크나이저 차이가 shot 차이로 새어 들어온다.
5 미만이 된 문항 수를 기록한다. 절단은 하지 않는다.

**채점** — log-likelihood. 프롬프트 뒤에 `" A"` `" B"` `" C"` `" D"` 를 이어 붙였을
때 이어붙인 부분의 로그확률 합이 가장 큰 것을 답으로 본다. 정답 열은 1~4 를
A~D 로 옮긴다. 지표는 정확도 하나.

**모델**

```
등록 비교     C0   artifacts/models/cpt_c0_qwen_main_seed42
              T2a  artifacts/models/cpt_t2a_none_main_seed42
descriptive   T2b  artifacts/models/cpt_t2b_mean_main_seed42
```

**판정** — 6과목을 합친 전체 문항(micro) 에서. 과목별 수치는 descriptive 다.

```
바닥 검사   C0 정확도의 95% bootstrap CI 하한이 0.25(찍기) 이하면
            D3 = "측정 불가 — 바닥". 아래 판정을 내리지 않는다

차이        d = acc(T2a) - acc(C0), 문항 단위 paired bootstrap 95% CI
            (10,000회, seed 0)

  CI 가 [-2%p, +2%p] 안에 전부 들어감   -> 같다        (예측 적중)
  CI 상한 < 0                          -> T2a 저하    (예측 반증)
  CI 하한 > 0                          -> T2a 향상
  그 밖                                -> 분해되지 않음
```

**±2%p 를 고른 이유.** 0.5B 의 KMMLU 정확도는 찍기(25%) 근처일 가능성이 크다.
그 구간에서 2%p 미만 차이를 "추론 능력 차이" 로 읽을 근거가 없다. 문항 수가
적어 CI 가 ±2%p 보다 넓으면 "분해되지 않음" 으로 끝난다 — 그것도 결과다.

**함께 적는 것 (descriptive)** — 과목별 정확도 · 한자를 1자 이상 품은 문항의
비율 · 그 문항만의 T2a−C0 차이. 마지막 것은 판정에 쓰지 않는다 (사후 분할이다).

**한계** — seed 42 단독이라 학습 seed 분산이 CI 에 없다. CI 는 **문항 표본 오차만**
반영한다. KMMLU 는 사람이 만든 한국어 시험이므로 "한국어 추론" 의 한 단면이지
전부가 아니다.

#### D1 — 표현 비용 (GPU 0시간, 한 줄 확인)

같은 부분집합에서 C0 / T2a 의 `tok_per_byte`.

`assert_byte_roundtrip` 이 보장하는 것은 **왕복 가능성** 이지 **토큰 비용** 이
아니다. 둘은 다른 것이라 별도로 잰다 — 다만 GPU 0시간이라 한 줄로 끝난다.

**예측: T2a 는 C0 의 2% 안.**

#### 뺀 것과 그 이유

| 뺀 것 | 왜 |
|---|---|
| 중국어 생성 품질 | 목표 언어가 아니다. 코퍼스도 저장소에 없다 |
| 한자 표현 가능 여부 | `assert_byte_roundtrip` 이 이미 보장한다 (시험 표본에 `混合` 포함) |
| KoBEST · HAE-RAE 를 이 축에 쓰는 것 | 이해·문화 과제라 추론 저하를 못 잡는다 |
| T2b 를 등록 비교에 넣는 것 | 제거 효과와 치환 효과가 분리되지 않는다 |

#### 한계를 먼저 적는다

- **부분집합이 균질하지 않다.** 한국어 한자 병기(耐震), 일본어 지명(徳庵),
  중국어 인용이 섞여 있다. "한국어 한자" 만의 효과로 읽으면 안 된다
- **T2a 는 논문의 EnKo 가 아니다.** EnKo 는 한자 스크립트를 통째로 지워 문자
  재고가 사라진다. T2a 는 빈도로 잘라 정자 상용자가 남았다. **EnKo 와 EnKoZh
  사이이고 EnKoZh 쪽에 가깝다.** 숫자를 직접 비교하지 않는다 (백본도 Qwen3 vs
  Qwen2.5 로 다르다)
- **중국어 본 평가는 못 한 것으로 limitation 에 적는다**
- D1~D3 이 전부 "차이 없음" 이어도 그것은 **이 세 측정에서** 없다는 뜻이다.
  생성 품질 · 장문 추론은 여전히 안 잰 것으로 남는다

#### 외부 문헌 근거 — HanjaBridge (2026-09-19 추가)

> **먼저 시점을 밝힌다.** D1~D3 의 예측은 2026-09-13 · 09-17 에 등록했고 결과는
> 2026-09-17 에 나왔다. **이 절은 그 뒤인 09-19 에 덧붙인 근거다.** 예측도 판정
> 경계도 바꾸지 않았고, 이 문단이 D3 의 결과를 "사전에 예측했다" 로 만들지도
> 않는다. 다만 근거가 **우리 데이터의 사후 관측이 아니라 외부 문헌** 이므로,
> 간체/정자 관측에 걸어 둔 제한("예측 근거로만 쓰고 결과로 인용하지 않는다")과는
> 성격이 다르다 — 이쪽은 논문 본문에서 기전 논의의 인용으로 쓸 수 있다.

arXiv 2507.10920 (HanjaBridge, Seungho Choi, 2025) 은 한중 한자 사전에서
**한국어에 대응하는 한자만** 골라 토크나이저에 넣었고, 공유 한자가 한국어–중국어
의미 정렬(cross-lingual transfer)을 만든다고 보고한다. 한국어 대응 한자는 **정자** 다.

여기서 우리 T2a 에 대한 기전 가설이 선다.

```
가설   한자가 한국어 추론에 기여하는 경로는 **정자** 를 매개로 한다
따름   간체 전용자를 지우는 것은 한국어 추론에 무해해야 한다
       정자를 지우면 손상이 나타나야 한다
사실   T2a 는 빈도 필터의 부수 효과로 간체 전용자를 잘랐고 정자(國 無 韓)는 남겼다
```

D3 의 결과(T2a − C0 = −0.21%p, CI [−1.05, +0.58])는 이 가설과 **부합한다.**
다만 부합은 검정이 아니다 — 이 설계는 "정자를 지웠을 때" 를 안 봤다.

#### 정자 절단 조건 — 2026-09-19 사전 등록 (아직 돌리지 않았다)

위 가설을 **반증 가능하게** 만들려면 반대쪽을 잘라 봐야 한다. 돌리기 전에 적는다.

          (간체 전용자는 남긴다). 제거 개수는 T2a 와 같은 30,000
평가      KMMLU 6과목 1,900문항, D3 와 완전히 같은 프롬프트 · 채점 · 판정 경계

```

**해석의 경계.** C0 가 찍기보다 약 6.5%p 위라 바닥 검사는 통과했지만, 0.5B 의
KMMLU 는 감도가 낮다. "빈도 필터가 추론 중간에 쓰이는 한자를 지웠다" 는 가설은
**이 감도에서 지지되지 않았다** 이지 반증된 것이 아니다. 한자를 품은 문항만의
차이(+0.71%p, CI ±3.5%p)는 사후 분할이라 인용하지 않는다.

### R1 판정 기준 정정과 R5 앵커 가정 — 2026-09-14 등록

2026-09-14 R1 을 돌린 뒤, **판정을 내리기 전에** 기준 자체가 성립하지 않는 것을
발견했다. 같은 종류의 결함이 R5 에도 있어 함께 등록한다.

> **R1 의 결과값(72.50%)은 이미 나와 있다.** 그래서 여기서 **새 임계값을
> 만들지 않는다.** 아래 규칙은 전부 이미 등록된 상수(효과 크기 바닥 5%p,
> 2 sigma)를 그대로 쓴다. 새 숫자를 고르면 사후 등록이다 ([RULES.md](RULES.md) 14번).

#### 무엇이 틀렸나 — 예산 "지점" 과 예산 "총량" 을 섞었다

[`SCHEDULE_P2.md`](SCHEDULE_P2.md) 의 R1 판정 기준은 *"회복률이 40MB
기준값(59.0~59.4%) 근처인가"* 였다. 그 기준값은 1차 T2b 곡선의 **40MB
체크포인트** 이고, R1 은 **총예산 40MB 의 종점** 이다.

```
1차 T2b30k @40MB   총예산 168.5MB 코사인의 24% 지점   lr 8.94e-06
R1 손상    @40MB   총예산  40MB 코사인의 100% 지점   lr 1.01e-06
```

LR 궤적이 다르므로 회복률을 나란히 놓을 수 없다. **대조군이 증거다** —
C0 의 40MB 지점이 1차 1.143644 vs R1 1.146431 로 C0 sigma 의 42배 차이다.
같은 40MB 를 같은 데이터로 본 대조군끼리도 이만큼 갈린다.

#### R1 을 판정하려면 없는 run 이 하나 필요하다

```
tied T2b (kot2b_v2_n30000_mean) 를 --budget-bytes 40000000 으로
1 seed. 나머지 학습 조건은 R1 과 완전히 동일
```

원장에 40MB 예산의 T2b run 이 하나도 없다. 이것이 나오기 전에는
**R1 을 "긍정" 으로도 "부정" 으로도 부르지 않는다.**

#### 판정 규칙 (새 상수를 만들지 않는다)

```
R_dmg    = R1 손상 조건의 회복률           (측정 완료: 72.50%)
R_t2b40  = tied T2b @40MB 종점의 회복률     (미측정)

같다      |R_dmg - R_t2b40| <  5%p        <- Q7 에 이미 등록된 효과 크기 바닥
다르다    |R_dmg - R_t2b40| >= 5%p
```

5%p 는 [위 "Q7"](#q7--tie-를-끊는다-2026-09-03-사전-등록-p2-의-본안) 에서
2026-09-03 에 정한 값을 그대로 가져온 것이다. R1 을 위해 새로 고른 것이 아니다.

두 회복률의 분모가 각자의 40MB C0 대조군이어야 한다. R1 은 자기 대조군을
이미 돌렸고, T2b 40MB 는 **같은 대조군을 재사용한다** — 예산·스케줄·드라이버가
같으므로 재측정할 이유가 없다.

#### 판정이 무엇이든 남는 교락 — 노출

`damage_rows` 는 `count_ko` 상위 40개를 골랐다 (16,847,004 ~ 3,320,117회).
1차 T2b 의 새 토큰은 168.5MB 전체에서 중앙값 143회다. **행당 노출이
10^4~10^5 배 다르다.**

K 보정은 손상 *크기* 만 맞췄고 노출은 안 맞췄다. 따라서 R1 은
"임베딩 손상 vs 토크나이저 치환" 을 깨끗하게 분리하지 못한다.

**이 교락은 이번 설계로 제거할 수 없다.** 손상 배율을 맞추면서 노출까지 맞추려면
저빈도 행을 대량으로 망가뜨려야 하는데, 그러면 K 가 수천으로 올라가 영어·코드가
함께 무너진다 (K>200 에서 시작, K=1,000 에서 영어 +29%). 보고할 때 한계로 적고
**"임베딩 손상 일반의 성질" 이라고 부르지 않는다.**

R2·R3 도 같은 교락을 물려받는다. 셋 다 같은 행 선택 규칙을 쓴다.

#### R5 의 앵커 — 가정을 명시하고 발동 조건을 건다

[`SCHEDULE_P2.md`](SCHEDULE_P2.md) Day 3 은 *"C0 기준선(1.137540)은 1차 것을
그대로 쓴다 — 같은 예산·같은 조건이라 재측정할 이유가 없다"* 고 적었다.
**같은 조건이 아니다.** 1.137540 은 *코사인* C0 의 바닥이고 R5 의 조건은
*상수* LR 이다. R1 과 같은 종류의 앵커 불일치다.

[위 "Q7"](#q7--tie-를-끊는다-2026-09-03-사전-등록-p2-의-본안) 은 이 원칙을 이미
갖고 있다 — *"회복률의 기준선을 tied-C0 이 아니라 untied-C0 의 BPB 로 잡는다.
이 대조군을 뺀 설계는 채택하지 않는다."* **R5 만 그 원칙에서 빠져 있었다.**

다만 크기가 다르다. 민감도는 `dR/dA = (B0-Bf)/(B0-A)^2` 이고 R~70% 에서 0.563 이다.

```
C0 바닥 이동   0.002   0.005   0.010   0.020   0.045
R 이동        0.11    0.28    0.56    1.13    2.53  %p
```

등록 A(71%)와 B(68.5%) 사이 밴드는 2.5%p 다. 이를 건너뛰려면 C0 바닥이
**0.044(C0 BPB 의 3.9%)** 움직여야 한다. 상수 lr 1e-5 를 끝까지 유지하면
담금질이 없어 그보다 작게 나빠질 것으로 보지만 — **재본 적이 없다.**

그래서 조건부로 등록한다.

```
R5 의 R 이 66.0~73.5% 밖에 떨어지면   1차 코사인 C0 앵커를 그대로 쓴다
그 안에 떨어지면                      상수 LR C0 을 1 seed 돌린 뒤 판정한다
```

66.0~73.5% 는 판정 밴드(68.5~71%)에 위 표의 최대 이동폭 2.53%p 를 양쪽으로
더한 것이다. 계산으로 나온 값이지 고른 값이 아니다.
추가 run 은 168.5MB 1개 ≈ 1h 45m 이고, 발동하지 않으면 비용 0 이다.

#### 같은 검사를 다른 사전 등록에도 걸었다

| 비교 | 앵커가 같은 조건인가 | 판정 |
|---|---|---|
| Q7 S2·3 / S4 | untied-C0 을 같은 예산·조건으로 돌린다 | **문제 없음** |
| R2 · R3 | R1 의 40MB C0 대조군 재사용, 예산·스케줄 동일 | **문제 없음** |
| D1~D3 프로브 | 1차 체크포인트끼리, 같은 예산·스케줄 | **문제 없음** |
| R1 | 1차의 *체크포인트* 와 비교 | **성립 안 함 — 위에서 정정** |
| R5 | 코사인 C0 을 상수 LR 조건의 앵커로 | **가정 명시 + 발동 조건** |

"조건이 바뀌면 대조군도 같은 조건에서 다시 잰다" 를 **P2 전체의 규칙으로** 둔다.
새 조건을 등록할 때 이 표에 한 줄을 더한다.

### P3 확장 — 2026-09-17 사전 등록

설계와 근거는 [`SPEC_P3.md`](SPEC_P3.md), 순서와 시간은 [`SCHEDULE_P3.md`](SCHEDULE_P3.md).
**이 절은 P3 의 어떤 run 보다 먼저 커밋한다.** 아래 예측은 P2 까지의 원장만 보고 적었다.

공통 규칙은 P2 와 같다 — 효과 크기 바닥 **5%p**, 경계 **2 sigma**, 사후에 경계를
옮기지 않는다 ([RULES.md](RULES.md) 14번). 회복률은
`R = (B0 - Bf) / (B0 - Bf(C0))` 이고, **앵커 C0 는 같은 스케줄 · 같은 예산 지점** 에서
잰다 (R1 판정 기준 정정 절의 규칙).

모든 CPT 명령은 비교 대상의 원장 argv 를 맞추고 `tools/compare_runs.py` 를 먼저
통과시킨다. 달라도 되는 필드는 각 항목에 적었다.

#### P3-A — 상수 LR 에서도 결국 멈추는가

```
조건    T2b(kot2b_v2_n30000_mean) · C0(Qwen2.5-0.5B), 상수 LR, 500MB, seed 42
평가    20MB 마다 + 168.5MB 에 한 번 더
저장    168.5MB 지점 체크포인트 (P3-F 가 쓴다)
허용    budget_bytes · pool 확장 필드 · 평가 지점 필드
```

**R5 재현을 내장한다.** W0 에서 두 가지를 고친 뒤 돌린다
([`SPEC_P3.md` §3](SPEC_P3.md)) — 워밍업을 예산 비율이 아니라 **바이트(3.37MB)** 로
고정하고, 문서 풀을 늘릴 때 **기존 50,000개의 순서를 보존** 한다. 그러면 168.5MB
까지의 데이터 순서와 LR 이 R5 seed 42 와 같다.

```
재현 검사   |Bf(168.5MB) - R5 seed 42 의 Bf| <= 0.001   (ko)
            실패하면 판정하지 않고 원인을 찾는다
```

0.001 은 1차의 같은 seed 재현 최대 편차 0.000421 의 두 배를 조금 넘고, 1차 T2b 의
seed 간 sigma 0.001234 보다 작다.

**판정** — 같은 run 쌍 안에서, 예산 배증당 회복률 증분을 비교한다.

```
I_mid  = R(160MB) - R(80MB)                         배증 1회
I_late = (R(480MB) - R(160MB)) / log2(480/160)      배증당으로 환산

I_late <= 0.5 x I_mid            -> 포화에 가깝다
0.5 x I_mid < I_late <= 0.85 x I_mid -> 감속이 이어진다 (점근선이 있는 쪽)
I_late > 0.85 x I_mid            -> 감속이 없다 (멱법칙 쪽)
```

`I_mid` 가 2%p 미만이면 비율이 불안정하므로 판정하지 않는다.

> **2026-09-19: 위 0.85 는 0.9 로 재등록됐다** (아래 "P3-A 예측 재등록", A 실행 전).
> 이 문단은 등록 시점 기록이라 고치지 않는다.

**예측: 가운데 칸 — 감속이 이어진다.** 근거는 R5 곡선의 배증당 증분이 이미
줄고 있었다는 것이다. 그 비율의 정확한 값은 W0 에서 도구가 R5 원장으로 계산해
표로 쓴다. **그 값이 (0.5, 0.85] 밖이면 이 예측을 P3-A 실행 전에 다시 등록한다**
(그 사실을 숨기지 않는다).

점근선 적합은 **exploratory** 다. 예산 범위가 1.4 decade 로 넓어지지만, 식별되는지는
적합을 해 봐야 안다. 식별되지 않으면 그렇게 쓴다.

#### P3-A 예측 재등록 — 2026-09-19 (A 를 돌리기 전, 결과를 보기 전)

위 등록은 *"그 값이 (0.5, 0.85] 밖이면 이 예측을 P3-A 실행 전에 다시 등록한다
(그 사실을 숨기지 않는다)"* 라고 적어 뒤였다. **그 조항이 발동했다.**

W0-9 도구가 R5 원장에서 계산한 값
([`reports/tables/p3_gates.md`](../reports/tables/p3_gates.md), `tools/p3_verdicts.py`):

```
40->80MB 증분 / 20->40MB 증분    0.869      <- 최초 등록 구간의 위
80->160MB 증분 / 40->80MB 증분   0.677      <- 구간 안
```

**구간을 (0.5, 0.9] 로 넓힌다.** 근거는 셋이다.

- R5 에서 관측된 두 비가 0.677 ~ 0.869 이다. 최초의 0.85 는 그 범위를 **가르는**
  값이라 "감속이 이어진다" 와 "감속이 없다" 를 나누지 못한다
- 감속이 전혀 없으면(멱법칙) 비는 1.0 이다. 0.9 는 그쪽과 아직 떨어져 있다
- 포화 경계 0.5 는 **그대로 둔다.** 이쪽은 관측이 건드리지 않았다

**바뀌지 않는 것:** 판정에 쓰는 구간 정의(세 칸), 증분 2%p 미만이면 판정하지 않는
규칙, 그리고 P3-A 의 판정이 **A 자신의 run** 에서 계산한 비로만 내려진다는 것.
R5 의 비는 예측의 근거일 뿐 판정에 들어가지 않는다.

**예측은 그대로다 — 가운데 칸(감속이 이어진다).**

#### P3-B — WSD 스케줄 (실무 처방)

```
조건    T2b · C0, 168.5MB, seed 42
스케줄  워밍업 2% -> 상수 -> 마지막 20% 에서 코사인으로 peak 의 10% 까지
        (감쇠 바닥 10% 는 P1 코사인과 같다)
허용    lr_schedule
```

**1차 지표는 T2b 의 절대 BPB 다** — 실무자가 원하는 것이 그것이다. 회복률은 2차 지표.

```
sigma   R5 T2b 3 seed 의 Bf sigma (상수 LR, 168.5MB) — 도구가 원장에서 계산
개선    Bf_WSD < Bf_const - max(2 sigma, 0.005)
구별 불가 |Bf_WSD - Bf_const| <= max(2 sigma, 0.005)
악화    Bf_WSD > Bf_const + max(2 sigma, 0.005)
```

0.005 는 BPB 의 효과 크기 바닥이다 (상수 LR T2b 의 약 0.34%). sigma 가 매우 작아
2 sigma 만으로는 실무상 의미 없는 차이가 "개선" 이 되는 것을 막는다.

**예측: 개선.** 마지막 감쇠 구간이 추가 이득을 준다고 본다 — WSD 를 쓰는 쪽의
일반적 관측이며 이 설정에서는 검증된 적이 없다. 회복률(WSD C0 앵커)은
**71% 이상** 으로 예측한다 — 코사인(65%)보다 상수(72%) 쪽에 있다.
영어 · 코드 부수 피해는 자기 조건 C0 대비로 함께 적는다.

**개선이면 T2b 를 seed 123 · 2026 으로 두 번 더 돌린다** (헤드라인 3 seed 규약).

#### P3-C — 조건 간 불변성이 상수 LR 에서도 유지되는가

```
조건    T2b10k(kot2b_v2_n10000_mean), 상수 LR, 168.5MB, seed 42
앵커    R5 의 상수 LR C0 (cpt_c0_qwen_r5_seed42) — 같은 스케줄 · 같은 예산
비교    R5 의 T2b30k 회복률
허용    model
```

```
유지    |R_10k - R_30k| < 5%p
깨짐    |R_10k - R_30k| >= 5%p 이고 2 sigma 를 넘는다
        sigma 는 R5 T2b30k 의 sigma_R 과 1차 T2b10k 의 sigma 를 회복률로 옮긴 값 중 큰 것
```

**예측: 유지.** 1차 코사인에서 두 조건은 20 · 40 · 80MB 지점에서 1%p 안에 있었고, R5 는

#### P3-D — R1 의 21.7%p 격차는 어디서 오는가

R1 에서 행 40개를 망가뜨린 모델은 72.50%, 같은 손상 배율의 T2b 는 50.79% 였다
(둘 다 코사인 40MB). 후보는 **행당 노출 · 손상 행 수 · 토큰화 변경** 셋이다.

**D0 — 보정 (학습 없음, 게이트).** `count_ko` 순위 구간별로 K 를 바꿔 가며 학습 전
손상 배율을 잰다 (`scripts/calibrate_k.py` 확장). 구간은 R1 과 같은 최상위, 그리고
행당 노출이 T2b 새 토큰 노출 중앙값의 10배 안에 드는 구간.

```
통과    노출 구간에서 K <= 30,000 으로 손상 배율 2.058 +- 0.05 에 닿는다 -> D2 를 돌린다
불통과  닿지 않는다 -> D2 를 돌리지 않고 "기존 어휘를 망가뜨려서는 노출과 손상 크기를
        동시에 맞출 수 없다" 를 결과로 보고한다
```

**D1 — permute K=40** (코사인 40MB, R1 과 같은 행). 분포와 노름을 보존하고 배정만
바꾼다. 앵커는 R1 의 C0 대조군.

```
같다    |R_permute - 72.50%| < 5%p
다르다  >= 5%p 이고 2 sigma 초과 (sigma 는 SPEC_P2 §4.2 의 보수적 상한 0.0013 을 R 로 옮긴 값)
```

**예측: 같다.** 행 · 노출 · 토큰화가 같으면 손상 종류는 회복률을 정하지 않는다.
학습 전 손상 배율이 mean 과 다르게 나오면 그 값도 함께 적는다.

**D2 — 노출 구간 손상** (D0 통과 시, 코사인 40MB). 토큰화는 바꾸지 않고 행당
노출과 손상 행 수를 T2b 쪽으로 옮긴다.

```
경계 61.6%  (= 50.79 와 72.50 의 중점)
R_band <= 61.6%  -> 격차는 노출 · 행 수 쪽에서 온다
R_band >  61.6%  -> 격차는 토큰화 변경 쪽에서 온다
```

**예측: 노출 · 행 수 쪽.** 드물게 보이는 행은 CPT 에서 기울기를 드물게 받는다.
이 설계는 노출과 행 수를 **함께** 옮기므로 둘을 서로 가르지는 못한다.

#### P3-E — 초기화를 완벽하게 하면 어디까지 가는가

T2b 코사인 168.5MB 최종 체크포인트(`cpt_t2b_mean_main_seed42`)의 **새 30,000행**
임베딩을 원본 Qwen2.5-0.5B 몸통에 옮겨 심는다(tied 이므로 출력 행도 같이 간다).
나머지 행과 몸통은 원본 그대로다. 토크나이저는 T2b.

```
측정    학습 전 BPB, 그리고 코사인 40MB CPT 후 BPB (R1 의 T2b 40MB 와 같은 설정)
지표    G = (Bf_T2b40 - Bf_oracle40) / (Bf_T2b40 - Bf_C0_40)
        Bf_T2b40 = cpt_kot2b_v2_n30000_mean_r1base, Bf_C0_40 = R1 의 C0 대조군
```

```
G >= 0.5   초기화가 격차의 절반 이상을 설명한다
G <  0.5   몸통 적응이 더 크다 — 더 좋은 초기화(ZeTT 류)로는 한계가 있다
```

**예측: G >= 0.5.** 이식된 행은 CPT 된 몸통과 함께 적응한 값이라 원본 몸통과
어긋나지만, 초기값 E1(부품 평균)보다는 훨씬 가깝다.

**하지 않는 주장:** ZeTT 의 성능. 이것은 "완벽한 초기화" 의 **상한 근사** 이고,
옮겨 심은 행이 다른 몸통과 함께 학습됐다는 교락이 남는다.

#### P3-F — T2b 의 과제 비용

D3 의 6과목은 **이미 T2b 결과를 봤다.** 그래서 P3-F 는 **KMMLU 나머지 39과목** 만 쓴다.

```
데이터   HAERAE-HUB/KMMLU revision d61b3f19e552c576bf5960dd24289763edc36a88
         나머지 39과목의 dev · test (train 제외). 받기 전에 사용자 확인
방식     D3 와 같다 — 5-shot, C0 토크나이저 기준 2048 토큰 shot 축소, 보기 글자 log-likelihood
모델     C0 코사인 · T2b 코사인 (1차 main)
         C0 상수 · T2b 상수 (P3-A 의 168.5MB 체크포인트)
```

```
바닥 검사  각 스케줄의 C0 CI 하한 <= 0.25 이면 그 스케줄의 판정을 하지 않는다

1차   d_cos = acc(T2b cos) - acc(C0 cos), paired 95% CI
      CI 상한 < 0 -> T2b 저하 · CI 가 [-2%p, +2%p] 안 -> 같다 · 그 밖 -> 분해되지 않음

2차   d_const - d_cos, 문항 단위 paired bootstrap 95% CI
      CI 하한 > 0 -> 상수 LR 이 과제 격차를 줄인다
```

**오염 검사 (판정 전에 한다).** 데이터 파이프라인의 "KMMLU 문항 중복 제거" 단계는
설계만 있고 구현되지 않았다 (`DATA_SOURCES.md`). 그래서 **CPT 에 실제로 쓴 문서 풀**
(50,000개, P3-A 는 확장분 포함)과 39과목 문항의 13-gram 겹침을 센다.

```
겹친 문항이 있으면  판정을 두 번 낸다 — 전체 문항과, 겹친 문항을 뺀 문항
                    둘이 다르면 **뺀 쪽을 판정으로 쓴다**
```

Qwen 사전학습 데이터의 오염은 알 수 없다. 네 모델이 같은 백본이라 조건 간
비교에는 같은 방향으로 작용하지만, 절대 정확도는 그 조건부로 읽는다.

**예측: 1차 저하, 2차 줄인다.** BPB 격차(+37.8% -> 상수 LR 에서 줄어듦)가 과제에도
옮겨 간다고 본다. 과목별 수치는 descriptive (KMMLU 과목 구분이지 우리 라벨이 아니다).

#### P3-G — 1.5B (탐침만 등록)

`scripts/probe_resources.py` 로 1.5B 전면 CPT 를 `micro_bs 1 · accum 16` (실효 배치 같음)
에서 잰다.

```
reserved <= 15,000MB  -> 1.5B 본 실험을 **별도 커밋으로** 등록한 뒤 돌린다
그 밖                  -> 1.5B CPT 는 이 장비에서 하지 않는다. 한계로 적는다
```

본 실험의 예측과 판정은 **탐침 결과를 본 뒤, 본 실험 전에** 등록한다. 탐침은
VRAM 과 속도만 알려 주고 회복률은 알려 주지 않으므로 사후 등록이 아니다.

### Candidate Gate 임계값 — 2026-08-30 확정

**T2 후보를 만들기 전에** 정했다. 결과를 보고 완화하면 §107 evaluation freeze 를
어긴다 ([RULES.md](RULES.md) 14번).

스펙 §17 의 원래 조건(영어 ≤5%, 코드 ≤10%)을 대조군 코퍼스로 실제 적용해보니
**HCX-SEED 와 A.X-4.0-Light 가 둘 다 탈락**했다.

```
HCX-SEED       한국어 -24~26%   영어 -0.5%   코드 +20.9%
A.X-4.0-Light  한국어 -26~40%   영어 +7.3%   코드 +26.6%
```

> 위 값은 **게이트를 정할 때 쓴 파일럿 측정** 이다. 이후 v1 전체 규모의 정식
> 측정에서는 A.X 코드가 +22.5%, HCX 코드가 +17.6% 로 나왔다
> ([`reports/tables/t2_sweep.md`](../reports/tables/t2_sweep.md)).
> 게이트 임계값은 **결과를 보기 전에 고정한 것이므로 그대로 둔다** — 사후에
> 정식 수치로 다시 맞추면 사전 등록의 의미가 사라진다 ([RULES.md](RULES.md) 14번).

A.X 는 실제 출시된 산업 토크나이저다. **출시된 제품을 거르는 게이트는 우리가
연구하려는 설계 지점 자체를 배제한다** — 임계값이 잘못 맞춰진 것이지 후보가
나쁜 것이 아니다. 그래서 두 층으로 나눈다.

| 층 | 영어 | 코드 | 동작 |
|---|---:|---:|---|
| **report** (스펙 §17 값) | 5% | 10% | 넘으면 **경고로 보고**. 거르지 않는다 |
| **hard** (파국 방지) | 25% | 40% | 넘으면 GPU 로 보내지 않는다 |

한국어 압축 개선 15% 이상은 **하드 조건 그대로** 둔다 (스펙 §17).

hard 값은 관측된 산업 지점(A.X: 영어 7.3%, 코드 26.6%)보다 넉넉히 위로 잡았다.
망가진 토크나이저가 학습 예산을 태우는 것만 막고, 정상 범위의 trade-off 는
전부 표로 보고한다 — 후보를 거르는 것보다 trade-off 를 보이는 것이 §16 의 목적이다.

이 결정으로 **Q2 의 답은 "통과/탈락"이 아니라 수치 보고가 된다.**
게이트가 후보를 거르지 않으므로, Q2 는 "영어·코드에 어떤 regression 이 생기는가"에
숫자로 답하고 스펙 §17 기준 초과 여부를 함께 적는다.

### 결론이 이렇게 나와도 완성이다

> 한국어 토큰을 31.2% 줄였으나, 통제된 CPT 후 Korean BPB 는 노이즈 플로어(σ=0.008)
> 이내에서 **구별되지 않았다**. 0.5B 규모에서 compression 의 이득은 품질이 아니라
> **지연과 메모리에만** 나타났다.

이건 실패가 아니라 답이다. 사후에 지표를 바꿔 "개선"을 만들어내지 않는다
([RULES.md](RULES.md) 14번).

## 자원 실측 — 계획의 근거

GPU  RTX 5070 Ti 16,303 MB    CPU  24 logical cores    RAM  31 GB
attention  mem_efficient+cudnn  (FLASH 는 이 torch 빌드에 없음)
```

### 학습 (Qwen2.5-0.5B full CPT, bf16, gradient checkpointing)

| seq | micro_bs | optimizer | VRAM reserved | 여유 | tok/s |
|---:|---:|---|---:|---:|---:|
| 1024 | 1 | AdamW | 5,990 MB | 10,313 MB | 6,292 |
| 1024 | 1 | **AdamW 8bit** | **5,300 MB** | **11,003 MB** | 6,287 |
| 2048 | 1 | AdamW 8bit | 7,716 MB | 8,587 MB | 7,489 |
| 2048 | 2 | AdamW 8bit | 13,326 MB | 2,977 MB | **9,089** |
| 4096 | 1 | AdamW 8bit | 13,326 MB | 2,977 MB | 8,795 |
| 8192 | 1 | AdamW 8bit | 23,132 MB | **초과** | 3,692 |

- **운영 설정: seq 2048, micro_bs 2, AdamW 8bit** — 13.3GB 로 16GB 안에 들어가고
  처리량이 가장 높다. seq 8192 는 VRAM 을 넘겨 호스트 메모리로 흘러 절반 속도가 된다
- 8bit optimizer 가 690MB 를 아끼면서 속도는 같다. 켜고 시작한다
- RAM 은 학습 중 1.7~1.9GB. 31GB 중 문제 없음

### GPU 시간 예산 — 병목이 아니다

9,000 tok/s 기준 **50M 토큰 CPT 한 번이 약 1.6시간**이다.

```
노이즈 플로어  3 seed × 5M      ≈ 0.5h
탐색 Stage 1~2                  ≈ 5h
본 실험 C0 / T2a / T2b × 50M    ≈ 5h
시스템 벤치마크                  ≈ 2h
                                ─────
                                 ≈ 13h
```

**GPU 는 전혀 병목이 아니다.** 12주 계획의 병목은 **데이터 전처리와 코드 작성**이다.
그래서 Step 1~2 에 절반을 배정한다.

### 반드시 지켜야 하는 것 — attention 백엔드

`attn_implementation="sdpa"` 만 주면 이 환경의 디스패처는 **MATH 로 폴백한다.**

| 입력 토큰 | 기본 (MATH) | 강제 (mem_efficient+cudnn) | 차이 |
|---:|---:|---:|---|
| 4,096 | 3,184 MB / 590 ms | 1,240 MB / 81 ms | 메모리 2.7배, 시간 7.4배 |
| 8,192 | 9,561 MB / 1,892 ms | 1,430 MB / 183 ms | **메모리 7.1배, 시간 10.3배** |

MATH 백엔드는 `n×n` attention 행렬을 실제로 만든다. 이걸 모르고 쟀으면
16k 이상은 전부 OOM 이고, 측정된 지연은 커널 비효율을 잰 것이지 토크나이저 효과가
아니게 된다. **Level 4 전체가 무의미해질 뻔했다.**

→ [RULES.md](RULES.md) 9번에 규칙으로 넣었고, `attn_backend` 를 `env_sha256` 에 포함시켰다.

### 알려진 한계 — 호스트 상한이 규모에 따라 다르게 작동한다

필터 통과율이 79.2% 로, 기대했던 90~92% 를 밑돈다. 사유는 하나로 몰려 있다.

```
host_cap        236,837  (15.79%)   파일럿 20k 에서는 4.3% 였다
too_short        40,710  ( 2.71%)   기준선 내
repeated_lines   34,602  ( 2.31%)   기준선 내
나머지              427  ( 0.03%)
```

`max_docs_per_host: 400` 이 **비율이 아니라 절대 건수**이기 때문이다. 2만 문서에서
400건은 점유율 2% 지만 119만 문서에서는 0.034% 라, 의도보다 60배 빡빡하게 걸린다.

절단된 상위 호스트는 tripadvisor 14,983 · expedia 9,452 · happycampus 8,980 ·
voakorea 8,120 · ko.wikipedia.org 6,652 다. 앞의 넷은 원래 막으려던 대상이지만
**위키백과가 400건으로 잘린 것은 손실**이다 — 학습 코퍼스의 약 1.2%, 백과 문체가
그만큼 얇아졌다. `encyclopedia` dev 가 0.4MB 인 직접적 원인이기도 하다.

v1 은 이대로 간다. 상한을 비율로 바꾸려면 코퍼스를 다시 만들어야 하고
(약 80분), 얻는 것이 1.2% 분량이라 지금 단계에서 감수할 이유가 없다.
다만 **토크나이저 결과를 해석할 때 백과 문체가 과소대표라는 점을 전제로 깔아야 한다.**
