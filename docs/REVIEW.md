# A. 방법론 — 가장 중요한 것들

## A1. 노이즈 플로어를 모르는 채 단일 시드로 후보를 거른다 ★최우선

스펙 §51 은 exploration 을 `seed=42` 하나로 돌린다. 비용 측면에서는 옳다.
그런데 **seed 간 분산을 모르면 "Korean BPB 1.207 vs 1.198" 이 의미 있는 차이인지
판단할 수 없다.** §17 Candidate Gate 가 노이즈로 후보를 거를 수 있다.

이건 스펙 전체에서 가장 큰 구멍이다. §52 는 capability 벤치마크의 bootstrap CI 만
다루고, **BPB 자체의 run-to-run 분산**은 다루지 않는다.

**보강**: Stage 1(1~5M 토큰)에서 **동일 config 를 seed 42/123/2026 으로 3회** 돌려
`σ_BPB` 를 먼저 측정한다. 이후 모든 비교는 `Δ > 2σ` 일 때만 "차이 있음"으로 보고하고,
그 미만은 **"구별 불가"로 명시**한다. 비용은 Stage 1 예산의 3배(≈15M 토큰)로 작다.

`docs/RULES.md` 10번을 이 내용으로 보강해야 한다.

## A2. 임베딩 비중 27.6% — 결론이 구조적으로 스케일 의존적이다 ★최우선

Qwen2.5-0.5B 에서 임베딩은 전체 파라미터의 **27.6%** 다. 1.5B 에서는 15.1%,
7B 급이면 대략 5% 수준이다.

즉 **0.5B 에서 측정한 "토크나이저 교체가 모델을 얼마나 망가뜨리는가 / CPT 로 얼마나
회복되는가" 는 큰 모델보다 체계적으로 과대 측정된다.** 토크나이저 수술이 건드리는
파라미터의 비중이 5배 다르기 때문이다.

스펙 §54 는 1.5B scale validation 을 "방향성 확인" 정도로 취급하는데,
**이 숫자를 보면 그건 선택이 아니라 필수 보정이다.**

**보강**:
- 모든 결과 표에 `embedding_share` 를 컬럼으로 넣는다 (0.5B: 27.6%, 1.5B: 15.1%)
- 회복 곡선(§71)의 x축을 토큰 수뿐 아니라 **"임베딩 파라미터당 학습 토큰"** 으로도 그린다
- 결론 문장에 "0.5B 기준"을 반드시 붙인다. 스케일 외삽을 주장하지 않는다

## A3. T1(Extend) vs T0 는 통제된 비교가 아니다

T1 은 vocabulary 를 늘린다 → 임베딩 파라미터가 늘어난다 (tied 이므로 lm_head 도 함께).
따라서 `T0 vs T1` 의 차이에는 **토크나이저 효과 + 파라미터 증가 효과**가 섞여 있다.
0.5B 에서 임베딩이 27.6% 이므로 이 오염은 작지 않다.

**T2(Substitution)만이 파라미터가 통제된 깨끗한 비교다.** 스펙 §12 가 "Vocabulary
Size ≈ Constant" 를 강조한 이유가 바로 이건데, §29 의 ablation 표(C0~C3)는 이 네 개를
동등하게 나열해서 그 차이를 흐린다.

**보강**: T1 결과에는 항상 `Δparams` 를 병기한다. 여유가 되면 파라미터 매칭 대조군
(T0 + 동일 수의 무의미 토큰 추가)을 하나 두면 주장이 훨씬 강해진다.

## A4. Equal Raw Data 조건에서 LR 스케줄이 어긋난다

같은 원문을 학습해도 토크나이저가 다르면 토큰 수가 다르고 → **optimizer step 수가
다르다.** 스케줄을 step 기준으로 정의하면 두 run 이 서로 다른 warmup 비율과 decay
곡선을 받는다. 그러면 §31 이 재려는 것이 tokenizer 효과인지 스케줄 차이인지 알 수 없다.

스펙 §29 의 "최대한 동일하게" 목록에 `Learning Rate`, `Scheduler` 는 있지만
**"스케줄의 x축을 무엇으로 두는가"** 가 빠져 있다.

**보강**: 스케줄을 **처리한 원문 바이트 기준**으로 정의한다 (`raw_bytes_seen`).
원장에 이미 컬럼이 있으니 구현 비용은 없다. 아니면 step 수를 맞추고 배치 토큰 수를
조정한다. 어느 쪽이든 config 에 명시해서 `config_sha256` 에 들어가야 한다.

## A5. Dev 과적합 / 다중비교

토크나이저 후보 ~10개 × 초기화 4개 × 체크포인트 5개면 dev 에서 수백 번 비교한다.
그중 최소값을 고르면 낙관 편향이 생긴다. Final Test 를 잠가둬도 **dev 자체가 닳는다.**

**보강**:
- dev 크기 하한을 정한다 — 도메인당 최소 5MB 원문 (BPB 표준오차를 충분히 줄이려면)
- 후보 선택은 "dev 최소값 하나"가 아니라 **`Δ > 2σ` 를 통과한 후보군**에서 멈춘다
- dev 조회 횟수를 원장에서 셀 수 있다 (`lm_metrics` 의 `split=dev` 행 수). 리포트에 적는다

## A6. CPT 코퍼스와 Qwen 사전학습 데이터가 겹친다

FineWeb-2 한국어는 Common Crawl 이고 Qwen2.5 도 CC 를 봤다. 즉 우리의 "continued
pretraining" 은 부분적으로 **이미 본 데이터의 재학습**이다.

치명적이진 않다 — C0(Original + 동일 CPT) 통제군이 이 효과를 흡수한다. 다만
§31 Equal Raw Data 의 해석에는 영향이 있다: "새 정보를 더 많이 봤다"가 아니라
"같은 정보를 다른 단위로 다시 봤다"에 가깝다.

**보강**: 결과 해석 문단에 이 한계를 적는다. 여유가 되면 CC 덤프 날짜가 Qwen2.5
컷오프 이후인 문서만 골라 보조 실험을 하나 둔다.

## A7. Fertility / 의미 단위 지표가 조작적 정의 없이 남아 있다

스펙 §14 는 `정보처리기사` 가 3조각이면 fertility=3, 1조각이면 1 이라고 한다.
**그런데 "정답 분절"이 무엇인지 정의되어 있지 않다.** 정의가 없으면
`tokenizer_metrics.tsv` 의 `fertility_mean` 컬럼을 채울 수 없다.

**보강**: 형태소 분석기를 하나 고르고 **버전을 고정**한다 (Kiwi 또는 mecab-ko).
`fertility = 토큰 수 / 형태소 수` 로 정의하고, 분석기 버전을 `config_sha256` 에 넣는다.
어절 기준(`tok_per_eojeol`)은 공백만으로 계산되니 그대로 두되, **Noisy Korean 도메인은
띄어쓰기가 깨져 있어 이 지표가 불안정**하다는 점을 병기한다.

# B. 시스템 평가 — Level 4 의 규모 문제

## B1. 0.5B 의 KV cache 는 애초에 작다 ★

Qwen2.5-0.5B 는 GQA KV head 가 **2개**뿐이다. KV cache = **12 KB/token**.
4096 토큰에 **48 MB**. 16GB GPU 에서 무의미한 크기다.

토크나이저로 시퀀스를 30% 줄이면 48MB → 33MB. **15MB 절약.**
이걸 "KV Cache -30%" 라고 쓰면 비율로는 맞지만 실질적 의미가 없다.

**보강**:
- KV cache / Peak VRAM 주장은 **1.5B 이상에서** 한다 (28 KB/tok, 4096 tok = 112MB)
- 0.5B 측정치는 "측정했으나 절대 규모가 작다"고 정직하게 적는다
- 더 나은 프레이밍: **모델 아키텍처별 KV cache 스케일링**을 함께 제시한다.
  같은 시퀀스 단축이 GQA 설정에 따라 몇 MB 를 아끼는지 표로 보이면
  "이 결과가 언제 중요해지는가"에 답이 된다

## B2. attention n² 항은 훨씬 긴 컨텍스트에서야 보인다 ★

Qwen2.5-0.5B 기준, layer 당 토큰당:

```
linear (q,k,v,o + MLP)  ≈ 14,909,440 MAC
attention (causal)      ≈ 896 × n MAC
```

두 항이 같아지는 지점은 **n ≈ 16,600 토큰**이다.

스펙 §111 의 최대 입력은 한국어 10,000자 ≈ Qwen 7,200 토큰. 이 길이에서 attention 은
전체의 약 30% 다. 토큰을 30% 줄였을 때 총 prefill FLOPs 감소는:

```
n=7,200 → 5,000 :  37% 감소  (선형이면 30%)
n=30,000 → 20,800 : 44% 감소  (선형이면 30.7%)
```

즉 **§75 가 말하는 "attention 영역이 절반으로" 라는 그림은 10,000자에서는 거의 안
보인다.** 초선형 이득이 7%p 뿐이다.

**보강**: §111 의 입력 길이를 **20,000 / 40,000자까지** 확장한다.
(Qwen2.5 컨텍스트 32,768 토큰 ≈ 한국어 약 50,000자가 상한)
그리고 **이론 감소율과 실측 감소율의 괴리 자체를 결과로 제시**한다 — §77 이 이미
그 방향을 지시하고 있고, 이게 오히려 좋은 발견이다.

## B3. HCX 와의 VRAM 비교는 토크나이저가 아니라 GQA 를 재는 것

HCX-SEED 는 KV head 가 **8개** — Qwen(2개)의 4배다. KV cache 가 48 KB/tok 대 12 KB/tok.
두 모델의 VRAM 을 비교하면 그 차이의 대부분은 아키텍처지 토크나이저가 아니다.

`docs/RULES.md` 4번(HCX/A.X 를 인과 실험으로 쓰지 않는다)을 **시스템 지표에도 명시적으로
확장**해야 한다. 지금 규칙 문구는 품질 지표만 염두에 둔 것처럼 읽힌다.

# C. 구현 함정 — 시작하면 바로 부딪힌다

## C1. `tie_word_embeddings=True` — LM head 가 곧 임베딩이다 ★

Qwen2.5 0.5B/1.5B 모두 tied 다. 결과:

- **E1 Mean 초기화의 근거가 입력 임베딩에만 성립한다.** 새 토큰을 구성 토큰들의
  평균으로 두는 것은 입력 쪽에서는 자연스럽지만, **출력 projection(어떤 토큰을 뱉을지
  결정하는 방향 벡터)에 대해서는 근거가 약하다.** tied 라서 한 번의 초기화가 둘 다 정한다.
- 스펙 §25 의 `LM Head TRAIN / TIED` 표기가 이 결정을 흐리게 적어놨다. **선택 사항이
  아니라 아키텍처 사실**이다.
- §68 의 A1(Embedding Only) ablation 은 tied 상태에서 "임베딩 + LM head 동시 학습"이 된다

**보강**: surgery 전에 **untie 할지를 명시적 실험 축으로 만든다.**
untie 하면 파라미터가 +136M (0.5B → 630M, +28%) 늘어나므로 공짜가 아니다.
최소한 "tied 로 진행했고 그것이 mean init 의 해석에 미치는 영향" 을 한 문단 적어야 한다.

## C2. 빈 슬롯 271개 — 기회이자 함정

`config.vocab_size(151,936) - len(tokenizer)(151,665) = 271`.

- **기회**: T1 에서 271개까지는 **resize 없이** 토큰을 추가할 수 있다. 파라미터 증가 0.
  작은 규모의 "파라미터 통제된 확장" 실험을 공짜로 하나 얻는다 (A3 의 보완재)
- **함정**: 이 271행은 **학습 신호를 거의 받지 못한 벡터**다. E1/E2 초기화에서
  기존 임베딩의 평균·표준편차를 계산할 때 이 행들을 포함시키면 통계가 오염된다.
  `[:len(tokenizer)]` 로 잘라내야 한다

## C3. byte fallback 토큰을 pruning 하면 토크나이저가 깨진다 ★

BBPE 는 임의의 바이트열을 표현하기 위해 **256개 바이트 토큰**이 필요하다.
이들은 코퍼스에서 개별 빈도가 낮게 보일 수 있어 **§19 의 pruning 후보로 잡히기 쉽다.**
하나라도 지우면 미지 입력에서 토크나이저가 실패한다.

스펙 §19 의 pruning 조건("저빈도 + 저중요 + 한국어/영어/code 핵심 아님")에
**이 항목이 없다.** 조용히 지나가면 T2 에서 확실히 사고가 난다.

**보강**: pruning 금지 목록을 코드 상수로 박는다 — 256 바이트 토큰 + special tokens +
BOS/EOS/PAD/UNK. 그리고 pruning 후 **랜덤 바이트열 왕복 테스트**를 단위 테스트로 넣는다.

## C4. Qwen BPE 는 단어만 추가해서는 확장되지 않는다

merge rule 이 없으면 추가한 토큰이 실제로 쓰이지 않는다.
[Qwen tokenization_note](https://github.com/QwenLM/Qwen/blob/main/tokenization_note.md) 와
[Qwen-Tokenizer-Pruner](https://github.com/KaihuaTang/Qwen-Tokenizer-Pruner) 참고.
T1 구현에서 가장 흔한 실패 지점이다.

**보강**: T1 구현 직후 **"추가한 토큰이 실제로 사용되는가"** 검증을 넣는다 —
새 토큰을 포함한 문장을 인코딩해서 해당 토큰 ID 가 나오는지 확인.

# D. 인프라 빈틈 — 지금 저장소의 실제 결함

## D1. 모델 revision 이 어디에도 기록되지 않는다 ★

스펙 §58 은 `model.revision: MODEL_COMMIT_HASH` 를 요구한다.
그런데 **`LEDGER.tsv` 에 해당 컬럼이 없다.** HF 저장소는 갱신될 수 있으므로
`model: qwen2.5-0.5b` 만으로는 계보가 끊긴다.

**보강**: `LEDGER_COLUMNS` 끝에 `model_revision` 추가 (컬럼은 뒤에만 붙인다).
`scripts/download_models.py` 가 받은 snapshot 해시를 기록하도록 확장.

## D2. 죽은 run 을 감지하지 않는다

OOM 이나 정전으로 프로세스가 죽으면 `status=start` 행만 남고 종료 행이 없다.
`validate_ledger.py` 가 이걸 경고하지 않아서, 원장이 "성공한 것처럼" 보인다.

**보강**: `start` 는 있는데 `ok`/`fail`/`abort` 가 없는 run_id 를 경고로 보고한다.

## D3. `merge=union` 은 중복 행을 만든다

`.gitattributes` 의 `merge=union` 은 충돌을 막아주지만, 두 브랜치에서 **같은 run 을
append 하면 양쪽 행이 모두 남는다.** 중복 검출이 없다.

**보강**: `(run_id, status, ts_utc)` 중복을 검사에 추가.

## D4. CI 가 없다 ★

훅은 **로컬 전용**이다. `--no-verify`, 다른 머신에서의 커밋, GitHub 웹 UI 편집,
그리고 훅 연결(`core.hooksPath`)을 잊은 클론 — 어느 것도 잡히지 않는다.
위생 시스템 전체가 "설정을 잊지 않았을 때만" 동작한다.

**보강**: GitHub Actions 로 push/PR 마다 `pytest` + `validate_ledger.py` +
`check_commit_msg.py`(푸시된 커밋 메시지 대상)를 돌린다. 이게 진짜 백스톱이다.

## D5. `configs/` 가 비어 있다

다음 세션이 복사할 예시 yaml 이 없다. `config_sha256` 을 어떻게 만드는지도 코드에만 있다.

**보강**: `configs/cpt/example.yaml` 과 `configs/evaluation/tokenizer.yaml` 을
스펙 §58 형식으로 하나씩 만들어 둔다.

# E. 신규성 — 유사 연구와의 거리

[`RELATED_WORK.md`](RELATED_WORK.md) 참조. 요약하면:

| 선행 | 겹치는 부분 | 우리의 차이 |
|---|---|---|
| **EEVE** | T1 + Embedding Alignment 골격 | 거의 동일. **재현으로 포지셔닝해야 한다** |
| **Token Pruning (2604.16235)** | T2 의 pruning | 그들은 vocab **축소**, 우리는 크기 유지 **치환** |
| **ZeTT** | 토크나이저 교체 전체 | 학습 불필요 접근. **baseline 으로 넣어야** 한다 |
| **FVT / FOCUS** | E1 / E2 초기화 | 이미 답이 나온 문제 |

**가장 큰 위험**: T2 의 차별점("축소 vs 치환")을 **말로만 주장하면 후발 연구로 보인다.**

**보강**: T2 를 두 조건으로 돌린다 —
`T2a: pruning 만 (vocab 축소, 그들의 설정)` vs `T2b: pruning + 한국어 치환 (크기 유지)`.
같은 파이프라인에서 직접 비교하면 그 자체가 결과가 된다. 추가 비용은 run 한 줄이다.

# F. 범위와 현실성

## F1. 스펙이 1인 1GPU 기준으로 너무 크다 ★

12 스텝 + 4 평가 레벨 + 6 페이즈 + A0~A5 파라미터 범위 ablation + layer-wise
representation 분석 + gradient 분석 + 3 seed + 1.5B scale validation.
**현실적으로 6개월 이상이다.** 절반에서 멈추면 포트폴리오로서 가치가 급감한다.

**보강 — 코어와 옵션을 미리 나눈다:**

**코어 (이것만으로 완결된 이야기)**
```
Step 1  데이터 파이프라인
Step 2  Level 1 토크나이저 벤치마크 (Qwen / HCX / A.X / Ours)
Step 3  T0 / T2a / T2b   ← T1, T3 는 뒤로
Step 6  E0 / E1 초기화 + Pre-CPT 평가
Step 8  0.5B CPT, C0 통제군 필수, Equal Raw Data
Step 12 시스템 벤치마크 (긴 컨텍스트 포함)
        + 노이즈 플로어 측정 (A1)
```

**옵션 (시간이 남으면)**
```
T1 Extend / T3 New BBPE
E2 Weighted / E3 Distillation
A0~A5 파라미터 범위 ablation
layer-wise CKA / gradient norm
1.5B scale validation
Equal Token Budget
3 seed 최종 검증
```

**단, A2(임베딩 비중) 때문에 1.5B scale validation 은 "옵션"에 두더라도
최소 1개 run 은 반드시 해야 한다.** 안 하면 결론의 유효 범위를 말할 수 없다.

## F2. 실패 조건이 정의되어 있지 않다

"한국어 BPB 가 개선되지 않으면 어떻게 하는가?" 스펙에 답이 없다.

이건 결함이라기보다 **놓친 기회**다. negative result 도 결과다 —
*"한국어 토큰을 31% 줄였지만 통제된 CPT 후 BPB 는 σ 이내에서 구별되지 않았다.
따라서 이 규모에서 compression 이득은 품질이 아니라 지연·메모리에서만 나타난다"*
는 **완결된 좋은 결론**이다.

**보강**: 시작 전에 "무엇이 나오면 무엇이라고 결론 낼 것인가"를 적어둔다.
사후에 정하면 §107 evaluation freeze 의 취지가 무너진다.

## F3. 일정·마일스톤이 없다

`docs/WORKFLOW.md` 의 Step 표에 목표 날짜와 GPU 시간 예산을 넣는다.
