# 도메인 라벨 — 무엇을 믿을 수 있고 무엇을 믿을 수 없는가

2026-08-30. 스펙 §16 의 도메인별 평가는 도메인 라벨이 맞다는 전제 위에 서 있다.
그 전제를 실제로 검증한 기록이다. **결론부터: 한국어 내부 도메인 세분화는
믿을 수 없고, 언어 간 구분(한국어/영어/코드)은 믿을 수 있다.**

---

## 요약

| 무엇 | 정확도 | 근거 | 쓸 수 있나 |
|---|---:|---|---|
| **언어 간** (한국어 / 영어 / 코드) | — | 라벨이 규칙이 아니라 **출처 데이터셋** | **그대로 쓴다** |
| 한국어 내부 `news` | 정밀도 60~89% | 블라인드 감사 | 정확도 병기하면 쓴다 |
| 한국어 내부 나머지 세분화 | **~55%** | 블라인드 감사 150건 | **쓰지 않는다** |
| `ko_en_mixed` 라벨 | 0~67% | 블라인드 감사 | 라벨 대신 `latin_share` 연속값 사용 |

그리고 이게 실제로 문제가 되지 않는 이유:
**압축률이 갈리는 것은 한국어 내부가 아니라 언어 간이다.**

```
한국어 내부   news -40.1%   blog -40.7%   web_general -39.8%   technical -38.4%
언어 간       한국어 -40%    영어 +7.3%    코드 +26.6%
```

한국어 내부 편차는 2.3%p 인데 언어 간 편차는 67%p 다. 세분화를 포기해도
§16 이 물어보는 것("한국어는 좋아졌는데 다른 데는 나빠졌는가")에는 답할 수 있다.

---

## 어떻게 여기까지 왔나

### 1차 — 규칙 v3, 예측 노출, 200건 → **88.0%**

무작위 200건을 뽑아 사람이 `gold_domain` 을 채웠다. 화면이 규칙 예측을 보여주고
`Enter` 로 수용할 수 있게 되어 있었다.

오류 24건 중 **17건이 한 가지 유형**이었다 — 지역·중소 언론사(경북일보, 제민일보,
국제신문, 전북일보, 뉴스1, 인사이트, 비즈한국 …)가 `web_general` 로 샌 것.
규칙에 전국 매체만 넣었기 때문이다.

```
news 정밀도  35/36 = 97.2%
news 재현율  35/52 = 67.3%     실제 뉴스의 1/3 을 놓친다
```

### 2차 — 규칙 v4, 예측 노출, 200건 → **100.0%, 무효**

v3 의 오류를 보고 규칙을 고쳤다(언론사 17곳 추가, 일반화 패턴, 규칙 순서 변경).
새 표본 200건(seed 123)을 뽑아 다시 라벨링했더니 **200/200 전부 일치**했다.

이건 결과가 아니다. `gold` 가 `predicted` 와 한 건도 다르지 않고 `reviewer_note`
는 0건이다. 예측을 보여주고 Enter 로 수용하게 만들었으니 전부 Enter 를 누르면
정의상 100% 가 나온다.

```
v3 오류율 12% 기준 200건 중 0건이 나올 확률          7.9e-12
뉴스 오류를 전부 고쳤다고 가정한 3.5% 기준            8.0e-04
```

**도구 설계 문제였다.** 예측을 보여주면 앵커링이 걸린다.

### 3차 — 블라인드, 150건 → **54.7%**

규칙 예측을 숨기고(강조 표시 제거, Enter 수용 차단) 150건(seed 2026)을 라벨링했다.

```
정확도 54.7% (82/150)

도메인          정답  예측  정밀도  재현율
news             53   37    81%    57%
web_general      62   89    52%    74%
blog              7   13    38%    71%
technical        12    1   100%     8%
community         6    1     0%     0%
ko_en_mixed      10    7     0%     0%
```

**v3 의 88% 도 앵커링으로 부풀려진 값이었다.** v3 역시 예측을 보여주는 화면에서
쟀다. 앵커링 없이 잰 첫 숫자가 54.7% 다.

### 원인 — 불공정한 비교였다

라벨링 안내에 **"호스트가 아니라 본문이 어떤 글인가"** 라고 적어놓고, 규칙은
**호스트로만** 판정한다. 사람은 내용으로, 규칙은 출처로 판단하니 어긋난다.

증거: 같은 `www.tripadvisor.co.kr` 문서가 사람 기준으로 한 건은 `technical`
(브라우저 지원 안내), 다른 건은 `ko_en_mixed` (호텔 스펙 나열) 로 갈렸다.
문서 단위 내용 판단이라 그렇다. 라벨 자체의 흔들림도 일부 섞여 있다.

### 4차 — 내용 신호 도입 시도 → **holdout 이 반박**

호스트만으로는 안 되니 본문 신호를 만들었다. 추측이 아니라 dev 105건을 읽고 뽑았다.

| 신호 | 관측된 예 | dev 평균 (해당 / 나머지) |
|---|---|---|
| 게시판 잔해 | `작성일`, `글쓴이`, `조회 : 14,985` | community 1.25 / 0.03 |
| 절차 어미 | `참조하십시오`, `지원하지 않는 브라우저` | technical 0.70 / 0.00 |
| 인용 보도 | `밝혔다`, `전했다`, `기자` | news 0.49 / 0.00 |
| 제품 스펙 | `모형: HS15025D`, `ISO 9001` | ko_en_mixed 1.00 / 0.01 |

추가 라벨링 없이 반복 개발하려고 표본을 **dev 105 / holdout 45** 로 나눴다
(`sample_id` 해시 기반, 결정론적). holdout 은 최종 1회만 봤다.

```
              dev(105)   holdout(45)
호스트만        58.1%       55.6%
+ 내용 신호     70.5%       53.3%      <- 반박
```

dev 에서 +12.4%p 였는데 holdout 에서는 오히려 내려갔다. **dev-holdout 격차
17%p 는 손으로 맞춘 정규식이 105건에 과적합한 전형적인 모습이다.** holdout
차이는 1건이라 노이즈이고, 개선을 주장할 근거가 없다.

그래서 `use_content_signals: false` 로 두고 코드는 남겼다
([`src/data/content.py`](../src/data/content.py)). 라벨이 더 모이면 다시 평가할 수
있고, 무엇을 시도했고 왜 채택하지 않았는지가 기록이다.
**dev 숫자만 보고 채택했다면 잘못된 규칙으로 전체 코퍼스를 라벨링할 뻔했다.**

## 그래서 어떻게 보고하는가

### 1층 — 언어 간 (신뢰. 그대로 쓴다)

`english` 와 `code` 는 **규칙이 매긴 라벨이 아니다.** 각각
`HuggingFaceFW/fineweb-edu` 와 `codeparrot/github-code-clean` 에서 왔다
([`scripts/run_control_pipeline.py`](../scripts/run_control_pipeline.py)).
출처가 다르므로 라벨이 확실하다.

§16 이 묻는 trade-off 는 여기서 답한다.

### 2층 — 한국어 내부 (참고. 정확도를 반드시 병기한다)

`news` 와 `기타` 2분할까지만 쓴다. `news` 정밀도는 블라인드 기준 81%, 규칙 v4
호스트 기준 dev 89% 다. 그 외 세분화(`technical`, `community`, `blog`)는
**보고하지 않는다** — 재현율이 0~40% 라 그 도메인의 수치가 무엇을 대표하는지
말할 수 없다.

원장 TSV 에는 세분화된 라벨이 그대로 들어간다. 데이터를 버리지는 않고,
**주장하지 않을 뿐이다.**

### `ko_en_mixed` — 라벨 대신 연속값

블라인드에서 정밀도·재현율 모두 0% 였다. 라벨로 쓰지 않는다.
대신 manifest 에 `latin_share` 를 연속값으로 기록해, 사후에 임의의 구간으로
문서군을 나눌 수 있게 한다. 도메인 라벨이 아니라 **문서 속성**이므로 규칙
정확도 문제를 우회한다.

`latin_share = latin / (hangul + latin)`. FineWeb-2 kor_Hang 2,868건 실측 분포:
중앙값 0.131, p75 0.259, p90 0.390, p95 0.498.

## 다시 잴 때

```bash
# 개발 중 (dev 로 몇 번이든)
.conda/python.exe scripts/eval_domain_rules.py --errors

# 최종 1회만
.conda/python.exe scripts/eval_domain_rules.py --holdout
```

새 표본이 필요하면 **반드시 블라인드로** 만든다:

```bash
.conda/python.exe scripts/audit_domain_rules.py --mode sample --shards 4 --seed <새 seed>
.conda/python.exe scripts/make_label_ui.py --blind --audit <위 파일> --out <html>
```

`--blind` 없이 만든 화면으로 정확도를 재면 앵커링으로 부풀려진다. 실제로 두 번 그랬다.
