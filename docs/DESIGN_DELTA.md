# 스펙 대비 설계 변경 — 무엇을 왜 바꿨는가

[`SPEC_KoTokenLab.md`](SPEC_KoTokenLab.md) 는 원본 복사본이고 **고치지 않는다**.
실행하면서 바꾼 것, 스펙에 없어서 우리가 정한 것, 스펙이 몰랐던 함정을 여기에
모은다. 이 문서가 없으면 우리가 발견한 것들이 커밋 메시지와 리포트에만 흩어져
남는다.

각 항목은 **스펙이 뭐라고 했는지 / 우리가 뭘 했는지 / 왜 / 근거는 어디에**
네 가지를 적는다.

---

## 1. 의도적으로 바꾼 것

### 1-1. Candidate Gate — 하드 조건을 이원화했다 (스펙 §17)

| | |
|---|---|
| 스펙 | 영어 악화 ≤5%, 코드 ≤10% 를 **하드 조건**으로 후보를 거른다 |
| 실제 | `report` (§17 값, 넘으면 경고) 와 `hard` (영어 25%, 코드 40%, 넘으면 GPU 금지) 로 나눴다 |
| 왜 | 원래 값을 대조군 코퍼스에 적용하니 HCX-SEED(코드 +20.9%)와 A.X-4.0-Light(영어 +7.3%, 코드 +26.6%)가 **둘 다 탈락**했다. A.X 는 실제 출시된 산업 토크나이저다. 출시 제품을 거르는 게이트는 우리가 연구하려는 설계 지점 자체를 배제한다 |
| 근거 | `configs/evaluation/tokenizer.yaml` 의 `gate` 절 주석. **T2 후보를 만들기 전에** 정했다 (§107 evaluation freeze) |

### 1-2. 도메인별 보고 — 7개에서 2개로 줄였다 (스펙 §16, §39)

| | |
|---|---|
| 스펙 | news / encyclopedia / blog / community / technical / ko_en_mixed / code 별로 BPB 를 보고한다 |
| 실제 | 한국어 내부는 `news` / `기타` 까지만. 언어 간(한국어/영어/코드)은 그대로 |
| 왜 | 블라인드 감사 150건에서 규칙 라벨 정확도가 54.7% 였다. community·ko_en_mixed 는 재현율 0%, technical 8%. **못 믿는 축으로 결과를 쪼개면 숫자가 아니라 잡음을 보고하는 것이다.** 반면 언어 간 라벨은 규칙이 아니라 출처 데이터셋이라 확실하다 |
| 잃은 것 | 거의 없다. 한국어 내부는 news 와 기타의 차이가 1.3%p 인데 언어 간은 62%p 갈린다. 결과가 갈리는 축과 라벨을 못 믿는 축이 서로 다르다 |
| 근거 | [`DOMAIN_LABELS.md`](DOMAIN_LABELS.md) |

### 1-3. Flash Attention 대신 SDPA (스펙 §120)

Windows 빌드가 불안정해서 PyTorch SDPA 로 대체하고 백엔드를 강제한다
(`EFFICIENT_ATTENTION` + `CUDNN_ATTENTION`). 강제하지 않으면 8,192 토큰에서
메모리 7.1배, 시간 10.3배가 된다. [`ENVIRONMENT.md`](ENVIRONMENT.md),
[`reports/tables/resource_probe.md`](../reports/tables/resource_probe.md).

### 1-4. 예산과 LR 스케줄까지 바이트 기준 (스펙 §26 을 더 밀고 나감)

| | |
|---|---|
| 스펙 | 학습 곡선의 x 축으로 `tokens_seen` 과 `raw_bytes_seen` 을 **함께 기록** 하라 |
| 실제 | 기록만이 아니라 **예산과 LR 스케줄 자체**를 바이트로 맞춘다 |
| 왜 | step 으로 스케줄을 짜면 토크나이저마다 같은 원문에서 step 수가 달라져 조건마다 다른 LR 궤적을 밟는다. 그러면 비교 대상이 토크나이저가 아니라 학습률이 된다 |
| 검증 | 같은 17.5MB 예산에서 C0 는 158 step, T2b 는 110 step 을 밟았다. 비율 0.696 이 Level 1 의 tok/char 비 0.698 과 일치한다. 토큰으로 셌다면 T2b 가 **43% 더 많은 원문**을 보고도 같은 예산이라 불릴 뻔했다 |

### 1-5. Embedding Alignment 단계를 통째로 뺐다 (스펙 §25 를 버림)

| | |
|---|---|
| 스펙 | 수술 이후 CPT 이전에 backbone 을 얼리고 embedding 만 학습한다 |
| 실제 | 그 단계가 없다. 수술 산출물에서 바로 CPT 로 간다 |
| 왜 | 손해를 안 내면서 제 일을 하는 lr 이 존재하지 않는다. 아래 3라운드로 확인했다 |

전체 표와 한계: [`reports/tables/alignment_probe.md`](../reports/tables/alignment_probe.md)

**1라운드 — 한국어 전용 정렬 (원장 `align_c0_qwen_v1_seed42`)**
C0 는 수술을 안 받아 임베딩이 이미 정렬돼 있다. 여기서 나빠지는 것은 전부
절차가 낸 손해다. 34MB 지점에서 영어 +8.8%, 코드 +13.1%, 회복 없이 **가속**.
T2a 도 거의 같았다 — 조건이 아니라 절차가 원인이다.

**2라운드 — 코퍼스에 영어·코드를 섞으면? (원장 `align_c0_qwen_probe_*`)**
가설: 영어·코드 토큰이 직접 gradient 를 받으면 제자리를 지킬 것이다.
17MB 씩 세 비율을 돌렸다. **반증됐다.**

| mix | ko | en | code |
|---|---|---|---|
| ko100 | -0.66% | +3.61% | +5.12% |
| ko80 | -0.64% | +3.64% | +4.22% |
| ko60 | -0.51% | +3.18% | +4.16% |

코퍼스의 40% 를 영어·코드로 채워도 영어 손해는 12% 줄어드는 데 그치고,
대신 한국어 이득도 같이 줄어든다.

**3라운드 — lr 이 원인인가? (원장 `align_*_probelr1e5*`)**
손해는 C0 에서, 이득은 임베딩이 실제로 망가진 T2b 에서 따로 쟀다.

| | 손해 (C0, 17MB) | 이득 (T2b) |
|---|---|---|
| lr 1e-4 | en +3.61%, code +5.12% | 3MB 에서 ko -15.24% |
| lr 1e-5 | en +0.01%, code +0.01% | 17MB 에서 ko -3.03% |

1e-5 는 아무도 안 다치게 하지만 T2b 도 안 고친다 — 5.7배 데이터로 1/5 만 갔다.
1e-4 는 T2b 를 빠르게 고치지만 영어를 3.6% 깎는다.

**기전** — backbone 이 얼면 모든 적응이 embedding 에서만 일어난다.
`tie_word_embeddings` 라 그 행렬 하나가 모든 언어의 표현이자 출력 로짓
방향이므로, 한국어 행만 크게 움직이고 나머지를 가만두는 lr 이 없다.
노름 보정(3-6)과 같은 기전이고, 같은 방식으로 반증됐다.

**예열이 필요하다는 근거도 없었다.** 노이즈 플로어에서 T2b CPT 를 정렬 없이
3번 돌렸고 전부 정상 종료했다 (`cpt_t2b_mean_noise_seed{42,123,2026}`).
CPT 는 backbone 이 풀린 채로 정렬 예산의 10배를 본다.

**무엇을 얻었나** — 조건 간 차이가 토크나이저와 수술만 남는다. 정렬 lr(1e-4)과
CPT lr(1e-5) 이 섞여 있던 교란도 같이 사라졌다. 스펙 §30 의 통제
("Original Tokenizer + Same CPT vs Korean Tokenizer + Same CPT")는 세 조건이
모두 정렬을 안 받으므로 그대로 성립한다.

**무엇을 잃었나** — 스펙 §25 는 정렬이 T2b 의 새 행에 도움이 된다고 가정했다.
그 가정은 검증하지 않고 버린 것이 아니라, 도움을 주는 설정이 손해도 함께
낸다는 것을 확인하고 버렸다. T2b 가 CPT 만으로 회복하는지는 이번 CPT 가 답한다.

## 2. 스펙에 없어서 우리가 정한 것

### 2-1. T2b 의 치환 토큰을 어떻게 고르는가 — 인접쌍 채굴

스펙 §12 는 "기존 tokenizer에서 거의 사용되지 않는 token을 제거하고 그 자리를
한국어 고효율 token으로 바꾼다" 까지만 말한다. **어떻게 고르는지는 없다.**
이것이 신규성의 실체이므로 여기에 적는다.

별도 한국어 BPE 를 학습하는 방법을 먼저 검토했으나 버렸다. 그 토큰이 Qwen
vocab 으로 표현될 보장이 없고 몇 조각으로 쪼개질지도 제각각이라 **슬롯 회계가
흐트러진다.** T2b 의 정의가 "vocab 크기 유지" 이므로 회계가 어긋나면 주장 자체가
깨진다.

대신 한국어 코퍼스를 **기존 Qwen 토크나이저로** 토큰화한 뒤 인접 토큰 쌍의
빈도를 센다. 가장 자주 붙어 나오는 쌍이 곧 합치면 가장 이득인 토큰이다.

```
새 토큰 1개 = merge 규칙 1개 = 슬롯 1개
```

부품 둘이 이미 vocab 에 있으므로 merge 규칙을 그대로 쓸 수 있고, 이득도
"출현 횟수 x 1토큰" 으로 정확히 떨어진다. BPE 가 원래 쓰는 탐욕 기준을 Qwen
vocab 위에 한 겹 더 적용하는 것과 같다.

`src/tokenizer/train.py`, [`reports/tables/t2_sweep.md`](../reports/tables/t2_sweep.md).

### 2-2. pruning 후보는 merge DAG 의 **잎** 이어야 한다 (스펙 §19 에 없음)

스펙 §19 의 조건은 "저빈도 + 저의미중요도 + 한국어/영어/code 핵심 아님" 셋이다.
여기에 넷째를 더했다.

BPE 에서 토큰 `AB` 는 규칙 `(A,B)->AB` 로만 만들어진다. 부품인 `A` 를 지우면서
규칙을 남기면 토크나이저가 깨지고, 규칙을 지우면 `AB` 가 도달 불가능한 死 슬롯이
된다. 연쇄적으로 번진다. 그래서 **다른 merge 의 부품으로 쓰이지 않는 토큰에서만**
고른다. Qwen2.5 는 151,643개 중 111,486개(73.5%)가 잎이라 여유가 충분하다.

### 2-3. "저의미중요도" 의 조작적 정의

직접 재지 않는다. **세 코퍼스(한국어·영어·코드) 모두에서 저빈도** 로 대신한다.
한국어에서 안 쓰인다고 지웠다가 영어·코드에서 쓰이는 토큰이면 Candidate Gate 의
regression 조건을 스스로 무너뜨리기 때문이다.

### 2-4. σ 는 조건마다 따로 잰다 (스펙 §51, §52 의 보강)

스펙은 seed 전략과 신뢰구간을 말하지만 **σ 가 조건에 따라 달라진다는 점**은 없다.
실측에서 한국어 σ 가 C0 0.000066, T2a 0.000090, T2b 0.001250 으로 **18.9배**
벌어졌다 (2026-09-13 전체 정밀도로 정정, `reports/tables/noise_floor.md`).
손상된 상태(BPB 2.38)에서 출발하는 조건은 seed 에 따라 회복 궤적이 갈린다.

C0 의 σ 를 T2b 비교에 쓰면 차이를 18.9배 과대 검출한다. **두 조건을 비교할 때는
큰 쪽 σ 를 기준으로 판정한다.** [`reports/tables/noise_floor.md`](../reports/tables/noise_floor.md).

T2a 가 C0 와 비슷한 것이 중요하다 — 원인이 "수술 여부" 가 아니라 **"수술로
손상됐는가"** 임을 보여준다. T2a 도 3만 토큰을 제거했지만 안 쓰이던 것이라
손상이 없고 σ 도 커지지 않았다.

## 3. 스펙이 몰랐던 함정 — 전부 실측으로 드러났다

### 3-1. pretokenizer 경계를 넘는 쌍은 절대 발화하지 않는다

Qwen 의 Split 정규식은 BPE 이전에 문자열을 자른다.

```
...|[^\r\n\p{L}\p{N}]?\p{L}+|\p{N}| ?[^\s\p{L}\p{N}]+[\r\n]*|...
                             ^^^^^  숫자는 한 자씩 고립
```

숫자는 낱개로 갈리고 글자(`\p{L}+`)와 구두점은 다른 세그먼트가 된다. BPE 는
세그먼트 안에서만 병합하므로 `" 1"`, `"20"`, `"다."` 같은 쌍은 merge rank 를
어떻게 줘도 발화하지 않는다.

이 확인 없이 채굴했을 때 **전체 인접쌍의 43.8%** 가 발화 불가능한 쌍이었고,
채굴 빈도 10만회 이상인 최상위 기증자 6개가 발화율 0% 였다. 고친 뒤 활성 슬롯이
59.0% -> 92.9%, 한국어 tok/char 이 -28.4% -> -30.2% 로 개선됐다.

**증상을 어떻게 잡았나**: 활성률만 보면 표본 부족과 구분이 안 된다. 채굴 빈도
구간별로 갈라 보니 발화율이 전 구간 ~60% 로 **평평했다.** 희소성이면 고빈도는
100%, 저빈도는 낮게 갈려야 한다. 평평하다는 것이 구조적 차단의 증거였다.

### 3-2. ByteLevel 토큰의 바이트 길이는 UTF-8 길이가 아니다

`"다"` 는 3바이트인데 vocab 에는 `'ëĭ¤'` 로 들어 있다. 이 **3글자가 곧 3바이트**다.
`len(token.encode("utf-8"))` 를 쓰면 6 이 나온다.

BPB 의 분모가 한국어에서 두 배로 부풀어 기준선이 0.5643 (틀림) vs 0.8048 (맞음)
으로 갈렸다. 언어마다 부풀림 비율이 달라서 그대로 뒀으면 비교 자체가 무의미했다.
2MB 를 읽었는데 4.07MB 로 집계되는 것을 보고 찾았다.

### 3-3. `added_tokens` 의 `special` 플래그를 믿으면 안 된다

Qwen2.5 는 added token 22개 중 **8개가 `special=False`** 다 — `<tool_call>`,
`<|fim_middle|>`, `<|file_sep|>` 같은 제어 토큰들이다. 웹 텍스트에 안 나오니
코퍼스 빈도가 0 이라 저빈도 pruning 후보 상위에 그대로 올라온다.

added token 은 정의상 merge 로 만들어지지 않고 예약된 ID 를 차지하므로,
플래그와 무관하게 전부 보호한다. 통계 파일의 `is_protected` 컬럼도 믿지 않고
`prune.py` 가 살아 있는 토크나이저로 다시 확인한다 — 그 컬럼은 만들 때의 판단이
굳어 있어서 보호 규칙을 고쳐도 따라오지 않는다.

### 3-4. `vocab_size` 151,936 은 정렬값이 아니다

토큰은 151,665개다. 128 배수로 올리면 151,680 이고, Qwen 은 **256칸을 더** 비워
뒀다. T2b 에 `padded_vocab_size` 를 다시 적용하면 256행이 잘려 "크기 유지" 라는
정의가 깨진다. T2b 는 원본 행 수를 그대로 쓴다.

### 3-5. 번호를 다시 매기면 config 의 특수 토큰 ID 가 범위 밖으로 나간다

T2a 에서 `config.eos_token_id` 가 151,643 인데 vocab 은 121,728 까지였다.
BPB 는 특수 토큰을 쓰지 않아 측정에 영향이 없었지만 생성과 CPT 가 깨진다.
`new_tok.bos_token_id` 만 보면 안 된다 — Qwen 은 tokenizer 에 BOS 가 없는데
config 는 들고 있어서, 옛 ID -> 토큰 문자열 -> 새 ID 로 되짚어야 한다.

### 3-6. 노름 보정은 도움이 아니라 해였다 — 가설이 반증됐다

부품 평균 초기화는 노름이 줄어든다(표준편차 0.01088 vs 살아남은 행 0.01488).
E0 에서 σ 를 맞춘 것과 같은 논리로 맞춰 주면 공정해질 줄 알았는데, 한국어 BPB 가
**2.3803 -> 3.0017 로 나빠졌다.**

`tie_word_embeddings` 때문이다. 그 벡터는 입력 임베딩이면서 **출력 로짓 방향**
이라, 크기를 키우면 아직 학습되지 않은 새 토큰을 모델이 더 자신 있게 예측한다.

증거는 영어다. 0.8115 -> 0.9448 로 함께 나빠졌다. 영어 문장에 새 한국어 토큰이
나올 리 없는데도 오른 것은 그 토큰들이 **softmax 분모를 통해 모든 문맥의 확률
분포를 침범** 했다는 뜻이다. 평균의 작은 노름은 결함이 아니라 보호 장치였다.

### 3-7. Equal-Raw-Data 회계는 근사로는 안 된다

문서의 바이트/토큰 비율을 조각에 곱해 배분하면, 조각에 이전 문서의 토큰이 섞여
있는데 현재 문서의 비율을 쓰므로 어긋난다. 한국어만 -0.38%, 한영 혼합 +0.73% 로
**부호까지 구성에 따라 뒤집혔다.**

크기보다 부호가 문제다. C0 와 T2b 는 같은 글에 대해 바이트/토큰 비율이 다르니
같은 예산에서 실제로는 다른 분량을 본다. 노이즈 플로어 σ 가 0.000058 로 좁아서
(학습 효과가 2σ 의 46배), **0.7% 의 데이터량 차이면 조건 간 차이를 그것만으로
만들어낼 수 있다.**

토큰마다 실제 바이트를 더하는 것으로 바꿨다. ByteLevel BPE 는 무손실 바이트
분절이라 토큰 바이트의 합이 원문 바이트와 정확히 일치한다. EOS 는 코퍼스 원문이
아니므로 0 바이트로 센다 — 세면 짧은 문서일수록 예산이 빨리 닳아 같은 문제가
다른 경로로 돌아온다.

### 3-8. 예산 "지점" 과 예산 "총량" 은 다른 조건이다 (2026-09-14)

| | |
|---|---|
| 스펙 | Equal-Raw-Data — 예산을 원문 바이트로 세면 조건 간 비교가 공정하다 (§26) |
| 실제 | **같은 바이트라도 그것이 긴 스케줄의 중간이냐 짧은 스케줄의 끝이냐가 결과를 바꾼다** |
| 왜 | LR 스케줄이 총예산에 대해 정의되므로, 같은 40MB 지점에서도 lr 이 8.94e-06 이냐 1.01e-06 이냐가 갈린다 |
| 근거 | 아래 |

R1 의 판정 기준이 *"회복률이 40MB 기준값(59.0~59.4%) 근처인가"* 였는데, 그
기준값은 1차 T2b 곡선의 40MB **체크포인트**(총예산 168.5MB 의 24% 지점)였고
R1 은 총예산 40MB 의 **종점** 이었다.

증거는 대조군이다. **같은 40MB 를 같은 데이터로 본 C0 두 개가 다르다.**

```
1차 C0 @40MB 체크포인트   1.143644
R1  C0 @40MB 종점         1.146431     차이 0.002787 = C0 sigma 의 42배
```

Equal-Raw-Data 는 **같은 스케줄 안에서** 조건을 비교할 때의 규약이지,
스케줄이 다른 run 끼리 같은 바이트 지점을 뽑아 비교해도 된다는 뜻이 아니었다.

**P2 전체 규칙으로 승격했다** — "조건이 바뀌면 대조군도 같은 조건에서 다시
잰다". 사전 등록마다 앵커 점검표를 둔다 ([`PLAN.md` "R1 판정 기준 정정"](PLAN.md)).
Q7 은 원래부터 이 원칙을 갖고 있었고(untied-C0 필수), R5 만 빠져 있어서
가정을 명시하고 발동 조건을 걸었다.

### 3-9. 같은 규칙이 세 곳에 따로 적혀 있으면 가장 비싼 지점에서 터진다 (2026-09-14)

| | |
|---|---|
| 스펙 | 없음 |
| 실제 | `run_id` 규칙이 생성기·검증기·커밋 훅에 따로 있었고, 훅에만 패턴 검사가 있었다 |
| 왜 | 40분짜리 run 을 다 돌린 뒤 커밋에서 거부당했고, 원장은 append-only 라 되돌릴 수도 없었다 |
| 근거 | `cpt_Qwen2.5-0.5B_r1ctrl_seed42` — 대문자·점 포함 |

`--model Qwen/Qwen2.5-0.5B` 를 주면 `make_run_id` 가 살균 없이 그대로 이어붙인다.
1차에서는 호출부가 `c0_qwen` 같은 깨끗한 슬러그를 넘겨서 드러나지 않았다.

고친 것 (`955baa9`, `458893a`):

```
생성기    _slug() 로 살균하고, 패턴에 안 맞으면 생성 시점에 예외
검증기    validate_ledger 가 같은 RUN_ID_RE 를 본다 — 스테이지 시점에 잡힌다
훅        그대로
테스트    세 곳의 패턴 문자열이 갈리면 깨진다
```

이미 기록된 행은 `LEGACY_RUN_IDS` 로 이름 면제한다. 데이터는 멀쩡하고
잘못된 것은 식별자 표기뿐이다. 목록이 늘어나면 그것이 버그다.

**같은 날 두 번째 사례**: 훅이 *"record 커밋에 코드 금지"* 만 보고 반대 방향을
안 봐서, `fix(infra)` 커밋 하나가 R1 의 원장 행·메트릭·run 디렉터리를 통째로
삼켰다. `precheck` 가 이제 양방향을 본다 — 판정 기준은 새로 붙은
`status=ok|fail` 행이다 (도는 중인 `start` 행과 스키마 이행은 통과시킨다).

### 3-10. 기본값이 함정이다 — `--eval-bytes` (2026-09-14)

| | |
|---|---|
| 스펙 | 없음 |
| 실제 | `--eval-bytes` 기본값이 1MB 라, 명시하지 않으면 40MB run 에 평가가 40회 붙는다 |
| 왜 | 일정표의 초/MB 는 `--eval-bytes 20000000` 으로 돈 1차 run 에서 뽑은 값이라 51% 낮게 잡혀 있었다 |
| 근거 | R1 실측 2,381초 = `180 + 40x25 + 40x30` |

평가는 비파괴적이고 `--eval-budget` 이 고정이므로 **BPB 는 바뀌지 않는다.**
바뀌는 것은 벽시계와 곡선 해상도뿐이라, 40MB run 에서는 오히려 유지할 값이 있다

[`SCHEDULE_P2.md` "run 하나가 얼마나 걸리는가"](SCHEDULE_P2.md).

### 3-11. run 의 git 계보는 진입 시점에 고정한다 (2026-09-17)

| | |
|---|---|
| 스펙 | §59 — 모든 행에 `git_commit` |
| 실제 | 행을 쓸 때마다 HEAD 를 읽었다. run 도중 코드를 커밋하면 start 행과 ok 행의 해시가 갈린다. `git_dirty` 는 커밋 전 원장 행 때문에 **모든 행에서 1** 이었다 |
| 왜 | D2 T2a run 이 start `6ce2e55` / ok `1105df7` 로 기록됐다. 실행된 코드는 앞쪽이다 |
| 근거 | `a478426` — `RunContext` 가 진입 시점 값을 모든 행에 쓰고, dirty 는 기록 경로를 세지 않는다 |

대기열로 이어 돌리는 run 은 **다음 run 이 새 코드로 돈다.** 해시는 이제 정확하지만,
대기열이 도는 동안 그 run 들이 쓰는 모듈을 커밋하지 않는 것이 여전히 맞다.

### 3-13. config 가 같아도 코드가 다르면 비교가 아니다 (2026-09-20)

2주차에 `cpt_c0_qwen_r5_seed42` 와 `seed123` 을 비교했다. `compare_runs` 는
`--allow seed` 로 config 를 통과시켰는데, 두 run 사이에 `src/` 와 `configs/` 를
건드린 커밋이 **9개** 있었다. 도구는 그것을 보지 못했다 — config 필드만 읽기
때문이다.

사람이 손으로 커밋을 훑어 "실제로 동작을 바꾼 것은 `2da591e` 하나" 를 확인했다.
그런데 그 손 대조가 `src/training/`·`src/utils/` 만 봐서 **`src/evaluation/` 을
건드린 4개를 놓쳤다.** (확인해 보니 `bpb.py` 변경은 독스트링뿐이고
`capability.py` 는 KMMLU 라 이 run 들의 dev BPB 에 안 들어간다. 결론은 안 바뀐다.)

**놓친 것이 결론을 안 바꿨다는 사실이 절차를 정당화하지 않는다.** 같은 방식으로
다음에도 훑으면 다음엔 바꾸는 것을 놓친다.

`compare_runs` 가 이제 두 run 의 `git_commit` 사이에서 `src/`·`configs/` 를
건드린 커밋을 세고, 있으면 **치명** 으로 다룬다. `tools/`·`tests/`·`docs/` 만
바뀐 구간은 걸리지 않는다 (`seed123` 대 `seed2026` 이 실제로 그렇다).
근거가 있으면 `--allow code` 로 연다 — `seed` 와 같은 취급이다.

### 3-14. 옛 `git_dirty=1` 은 코드 오염이 아니다 (2026-09-20)

3-13 을 만들면서 T2b 상수 3 seed 가 전부 `dirty=1` 인 것이 드러났다. 그대로
"커밋 안 된 코드 위에서 돌았다" 고 적을 뻔했다.

틀렸다. `a478426`(2026-09-17) **이전** 의 `git_dirty` 는 `experiments/` 같은
기록 경로도 dirty 로 셌고, run 은 돌면서 자기 원장 행을 append 한다. 그 `1` 은
대개 **그 run 자신이 만든 원장 행** 이다.

그렇다고 "코드는 깨끗했다" 도 아니다. 둘을 구분할 수 없다.
`gitinfo.dirty_is_code_scoped(sha)` 가 `True/False/None` 으로 답하고, 두 도구가
그 답에 따라 문구를 바꾼다. **모르는 것은 모른다고 적는다.**

## 5. 알려진 한계

- **호스트 상한이 규모에 비례하지 않는다.** v1 코퍼스에서 `host_cap` 이 15.79% 를
  걷어냈고 위키백과가 6,652건에서 400건으로 잘렸다 (코퍼스의 약 1.2%). 백과 문체가
  과소대표라는 전제로 결과를 읽어야 한다. `max_host_share` 를 만들어 뒀지만
  v1 은 재실행하지 않았다 ([`PLAN.md`](PLAN.md) "고정된 계보")
- **기증 토큰 7.1% 가 여전히 미발화다.** 인접쌍끼리의 경쟁이다 — `(A,B)` 와
  `(B,C)` 가 같은 `B` 를 두고 다투므로 둘 다 발화할 수 없다. 다회 라운드로 줄일 수
  있지만 라운드마다 코퍼스를 다시 토큰화해야 하고 여지가 7% 라 하지 않았다
- **σ 는 17.5MB 예산에서 잰 값이다.** 본 실험(168.5MB)에서는 궤적이 더 갈릴 여지가
  있어 하한으로 다뤄야 한다. (2차 R5 는 168.5MB 에서 T2b 3 seed 를 재서 sigma_R
  0.026%p 를 얻었다 — 상수 LR 조건에 한한다)
- **코퍼스 오염 제거(KMMLU 등 문항 겹침)는 구현되지 않았다.** 과제 평가 수치는 그
  조건부로 읽는다. P3 W0-12 에서 CPT 풀과의 겹침을 센다
- **Pre-CPT BPB 예산이 언어당 2MB 다.** 초기화 방법 차이가 배수 단위라 갈리기엔
  충분했지만 미세한 차이를 볼 때는 부족하다
