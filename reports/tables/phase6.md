# Phase 6 — 결론의 유효 범위 (A · C · E)

측정 2026-09-02. Q1~Q6 가 닫힌 뒤, **코어의 결론이 어디까지 적용되는지** 를
정하는 후속 셋이다. 사전 등록은 [`../../docs/PLAN.md`](../../docs/PLAN.md)
"Phase 6" 절 — 셋 다 돌리기 전에 예측을 적었다.

| | 물음 | 예측 | 결과 |
|---|---|---|---|
| **A** | 부정 결과가 0.5B 만의 것인가 | 손상이 1.58배로 줄 것 | **틀렸다.** 2.324배로 커졌다 |
| **C** | 회복이 멎을 때 임베딩 기울기가 죽는가 | 죽지 않는다 | **맞았다** |
| **E** | 메모리 절감이 동시 처리와 처리량으로 얼마나 가는가 | 동시 1.43배, 처리량은 그보다 작다 | **절반 맞았다.** 동시 1.40배, 처리량 1.60배 |

---

## A. 스케일 — 손상은 커질수록 커진다

Qwen2.5-1.5B 에 같은 T2b 수술을 걸었다. 1.5B 는 vocab 도 merges 도 0.5B 와
**완전히 같아** 토크나이저 산출물을 그대로 얹을 수 있다. 학습 없이 수술 +
Pre-CPT BPB 만 재는 30분짜리다.

| | 임베딩 비중 | 기준선 | 수술 후 | 손상 배율 |
|---|---:|---:|---:|---:|
| 0.5B | 27.6% | 1.1569 | 2.3803 | 2.058배 |
| **1.5B** | **15.1%** | **0.9921** | **2.3060** | **2.324배** |

예측은 "임베딩 비중에 비례해 1.58배" 였다. **틀렸다.** 비중이 절반이 됐는데
손상은 줄기는커녕 커졌다.

**이유는 분모에 있다.**

```
수술 후   2.3803 -> 2.3060   -3.1%   거의 안 움직인다
기준선    1.1569 -> 0.9921  -14.2%   크게 좋아진다
```

**수술 후 상태는 스케일과 거의 무관하다.** 부품 평균 초기화가 정보를 잃는
정도가 모델 크기에 딸려 있지 않기 때문이다. 반면 기준선은 커질수록 좋아진다.
**큰 모델은 잃을 것이 더 많고, 수술은 둘 다 거의 같은 자리로 되돌린다.**

영어(+0.13%)와 코드(+0.73%)는 0.5B 와 마찬가지로 거의 안 움직인다.

**이것이 답하지 않는 것**: 1.5B 가 CPT 로 **더 잘 회복하는지** 는 모른다. 이
측정은 손상이지 회복력이 아니다. 큰 backbone 이 더 잘 메울 가능성은 열려
있고 그건 1.5B CPT 를 돌려야 안다 (약 5시간).

## C. 기울기 — 신호는 있는데 못 따라간다

`train_curve` 의 `grad_norm_emb` / `attn` / `ffn` 을 처음으로 채웠다. 스키마에
컬럼이 있는데 학습 루프가 오래 비워 뒀다. 클리핑 **전에** 잰다 —
`clip_grad_norm_` 은 grad 를 제자리에서 줄이므로 순서가 결과를 바꾼다.

| 예산 | ko BPB | emb | attn | ffn | lr | emb/attn |
|---:|---:|---:|---:|---:|---:|---:|
| 20MB | 1.7441 | 4.78 | 2.09 | 2.42 | 9.78e-06 | 2.28 |
| 60MB | 1.6038 | 3.22 | 2.00 | 2.23 | 7.62e-06 | 1.61 |
| 80MB | 1.5822 | 3.05 | 1.79 | 2.09 | 6.00e-06 | 1.70 |
| 100MB | 1.5726 | 3.39 | 1.86 | 2.30 | 4.31e-06 | 1.82 |
| 160MB | 1.5675 | 2.98 | 1.90 | 2.14 | 1.06e-06 | 1.57 |

**예측대로 임베딩 기울기가 죽지 않는다.** 4.78 에서 2.98 로 내려오지만 바닥을
치지 않고, 끝까지 attn 의 1.57배로 남는다.

그런데 같은 구간에서 BPB 는 100MB 이후 0.005 밖에 안 움직인다.
**모델은 "여기를 이렇게 고쳐라" 라는 신호를 끝까지 받고 있는데 못 따라간다.**
병목은 최적화가 아니다.

**80MB → 100MB 에서 기울기가 오히려 오른다** (3.05 → 3.39). 같은 구간에서
lr 은 6.0e-06 → 4.3e-06 으로 떨어진다. 업데이트는 `lr x grad` 이므로, lr 이
줄자 손실 표면에서 못 내려가고 기울기가 다시 커진 모양새다 — **LR 이 회복을
끊고 있다는 방증** 이고, 등토큰 run 이 68.2% 까지 간 것과 같은 방향이다
([`phase4.md`](phase4.md)).

### 덤 — 같은 시드 재현성을 처음 쟀다

이 run 은 어제 T2b run 과 모델·예산·풀·시드·평가 설정이 전부 같고 `tag` 만
다르다. 그래서 **같은 시드 재실행 분산** 을 잴 수 있었다 — 한 번도 안 본 축이다.

```
9개 지점 최대 편차 0.000421   조건 sigma 0.001234   비율 0.34
```

같은 시드 재실행 분산이 시드 간 분산보다 작다. **sigma 를 시드 분산으로 잡은
것이 과소평가가 아니었다** — 지금까지의 모든 판정이 그대로 유효하다.

다만 편차가 9개 지점 **전부 같은 부호(+)** 로 쏠렸다. GPU 비결정성이
무작위였다면 부호가 섞였을 것이다. 오늘 추가한 기울기 계측이 연산 순서를
미세하게 바꾼 흔적으로 보인다. 크기가 sigma 의 1/3 이라 판정에는 영향이
없지만 완전한 무작위 잡음이 아니라는 것은 남긴다.

계측기는 공짜가 아니다 — VRAM 을 553MB 더 쓴다 (11,382 → 11,935).
임베딩 기울기(151,936 x 896 = 136M 원소)의 노름을 fp32 로 올려 계산하면서
임시본이 생기는 것으로 보인다 (fp32 로 545MB, 관측치와 맞는다). 가설이다.

## E. 배치 — 처리량은 배치가 아니라 압축에서 온다

Q6 본 측정은 배치 1 단일 요청이었다. "메모리를 30% 아끼므로 요청을 1.4배
받는다" 를 그 표로는 말할 수 없었다.

20,000자 원문 (C0 13,704토큰 / T2b 9,543토큰), prefill 만, warmup 5 / 측정 20회.

| 배치 | C0 처리량 | C0 reserved | T2b 처리량 | T2b reserved |
|---:|---:|---:|---:|---:|
| 1 | 3.76 | 1,668 | 6.13 | 1,510 |
| 8 | 3.85 | 6,778 | 6.15 | 5,036 |
| 16 | 3.84 | 12,536 | 6.17 | 9,038 |
| **20** | **3.85** | **15,412** | 6.17 | 11,048 |
| 22 | 2.84 | 16,848 | 6.18 | 12,040 |
| **28** | — | — | **6.18** | **15,048** |
| 30 | — | — | 4.97 | 16,054 |

장치 총량 16,303MB. 굵은 줄이 **성능이 유지되는 마지막 배치** 다.

### 결과

```
동시 처리 수   C0 20  ->  T2b 28      1.40배   (예측 1.43배 — KV 절감분)
정점 처리량    3.85   ->  6.18 seq/s  1.605배
배치1 prefill  265.8  ->  163.2 ms    1.629배
```

**예측이 절반 맞았다.** 동시 처리 수는 KV 절감만큼(1.40배) 늘었다. 그러나
처리량 이득이 "그보다 작다" 는 예측은 **틀렸다** — 1.605배로 더 크다.

논거였던 "배치가 커지면 연산이 먼저 병목이 된다" 는 관찰은 맞았고 결론이
거꾸로였다. **연산 병목이면 처리량은 메모리 절감(1.43배)이 아니라 연산
절감을 따라간다.** prefill 이 1.629배 빨라지니 처리량도 1.605배다. 두 수가
붙는 것이 그 증거다.

### 예측하지 못한 것 — 배치는 처리량을 사지 않는다

```
C0    배치  1 -> 20    처리량 3.76 -> 3.85    +2.4%
T2b   배치  1 -> 28    처리량 6.13 -> 6.18    +0.8%
```

**배치를 20~28배로 늘려도 처리량이 거의 그대로다.** 13,704 토큰짜리 시퀀스
하나가 이미 GPU 를 포화시킨다. 배치가 사는 것은 처리량이 아니라 **동시성**
이다 — 같은 총 처리량으로 더 많은 요청을 동시에 물고 있을 수 있을 뿐이다.

그래서 정확한 진술은 이렇다:

> 동시에 물 수 있는 요청이 **1.40배**, 초당 처리하는 문서가 **1.60배**.
> **후자는 배치가 아니라 압축 자체에서 나온다.**

긴 한국어 문서를 서빙한다면 배치 튜닝보다 토크나이저가 크다는 뜻이다.

### 이 측정에서 두 번 넘어졌다

**1. OOM 을 정지 조건으로 쓴 설계가 이 플랫폼에서 성립하지 않는다.**
Windows WDDM 드라이버는 장치 메모리가 모자라면 시스템 RAM 으로 흘린다 —
죽지 않고 느려지기만 한다. 첫 시도에서 배치 26 이 peak_alloc 17,495MB 로
장치 총량을 넘겼는데도 OOM 이 안 났다. 그대로 뒀으면 배치 48 까지 느려지기만
하다 "최대 배치 48" 이라는 무의미한 답이 나왔을 것이다. 중단하고 abort 행을
사유와 함께 남겼다.

**2. 경계 변수를 잘못 골랐다.** allocated 가 아니라 **reserved** 다 —
캐싱 할당자가 잡아 둔 것이 실제로 장치를 차지한다. allocated 로 재면 C0 가
배치 24 까지 "들어간다" 고 나오는데 거기서는 이미 처리량이 39% 무너져 있다.
실제로 그렇게 보고했다가 `peak_reserved` 를 보고 고쳤다. **컬럼을 둘 다
남긴 것이 값을 했다** — 다시 안 돌리고 사후에 올바른 경계를 적용할 수 있었다.

## 한계

- **A 는 손상만 잰다.** 1.5B 의 회복력은 모른다. Pre-CPT 두 점(0.5B, 1.5B)으로
  "스케일 무관" 을 말하는 것이므로 7B 로의 외삽은 근거가 약하다
- **C 는 T2b 한 조건이다.** C0 나 T2a 의 기울기 궤적과 대조하지 않았다.
  "임베딩 기울기가 크다" 가 손상 때문인지 확인하려면 대조군이 필요하다
- **C 의 LR 해석은 방증이지 증명이 아니다.** 상수 LR 로 돌려야 닫힌다
  (PLAN 의 B, 미실행)
- **E 는 한 길이(20,000자), 한 GPU, prefill 만이다.** 짧은 입력에서는 배치가
  처리량을 살 여지가 있다 — 시퀀스 하나로 포화되지 않기 때문이다. 이 표는
  긴 문서에 대한 진술이다
- **E 의 절대 배치 수는 데스크톱이 쓰는 VRAM 에 딸려 있다.** 두 조건을
  연달아 재서 비(1.40배)는 튼튼하지만 절대값(20, 28)은 조건부다.
  시작 여유는 두 run 모두 14,045MB 였고 config 에 남아 있다
